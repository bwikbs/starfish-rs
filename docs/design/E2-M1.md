# E2-M1 — text-decoration, list markers, real inline-block (design note)

Scope: three small extensions to the existing static pipeline, touching
`starfish-style`, `starfish-layout`, `starfish-paint`. No JS, no networking.

1. **text-decoration** — `underline` / `overline` / `line-through`, single solid
   line in the text color, painted as fill-rects under/over/through each text
   run.
2. **List markers** — `list-style-type` (`disc`/`circle`/`square`/`decimal`/
   `none`) at `list-style-position: outside`. `<ul>`/`<ol>` items get a marker
   box in the left gutter.
3. **Real `inline-block`** — `Display::InlineBlock` becomes an *atomic inline*:
   it runs its own block layout to get a used width/height, then occupies its
   margin-box width as a single unit on the line, wrapping like a word.

Guiding rule (project CLAUDE.md "Simplicity First"): only the minimum each
feature needs. Deviations from real CSS are called out in §6.

This note is pinned to the **real** current APIs read from the source (see the
quoted signatures inline), not an idealized model.

## 0. Inputs (recap of the real APIs touched)

From `starfish-style` (`crates/style/src/{computed,properties,ua,lib}.rs`):

- `ComputedStyle` — plain struct of public fields; built by
  `ComputedStyle::initial()` then mutated by `apply_declaration`. `inherit_from`
  copies the inherited set onto a fresh `initial()`.
- `Display::{Block, Inline, InlineBlock, None}` already exists.
- `apply_declaration(style: &mut ComputedStyle, decl: &Declaration, ctx: EmContext) -> bool`
  — big `match decl.name.as_str()`. Components are `&[Component]` with
  `Component::{Keyword(String), Number(f32), Dimension{value,unit}, Color, Comma, Str, …}`.
- UA sheet is one `const UA_CSS: &str` parsed by `parse_stylesheet`.

From `starfish-layout` (`crates/layout/src/{boxtree,block,inline,dimensions,measure}.rs`):

- `BoxKind::{BlockContainer, InlineBox, AnonymousBlock, TextRun, LineBox}`.
- `LayoutBox { kind, style: BoxStyleRef, text: Option<String>, dimensions: Dimensions, children: Vec<LayoutBox> }`,
  with `is_inline_level()` = `InlineBox | TextRun`.
- `build_node`/`build_children`/`wrap_anonymous_blocks` generate the tree;
  currently `Display::Inline | InlineBlock => BoxKind::InlineBox` (inline-block
  collapses to plain inline).
- `layout_block` → `layout_block_children` (all-inline → `layout_inline`, else
  block stacking). `layout_inline` flattens the subtree to words via
  `collect_words`, greedily breaks into `LineBox`es of `TextRun` fragments.
- `Dimensions` with `content: Rect`, `padding/border/margin: EdgeSizes`, and
  `padding_box()/border_box()/margin_box()`.
- `TextMeasurer::{measure, line_metrics}`; `DefaultMeasurer`, `FontMeasurer`.

From `starfish-paint` (`crates/paint/src/{display,font,raster}.rs`):

- `PaintCmd::{FillRect{rect,color}, GlyphRun{origin,text,font_size,weight,color,ascent}}`.
- `paint_box` walks pre-order: `TextRun` → `emit_text`, else
  `emit_background`+`emit_borders`, then recurse into children.
- `FontDb::{advance_width, line_metrics, rasterize_glyph}`; `FontMeasurer` wraps
  it for layout so measuring == painting.

## 1. Style additions (`starfish-style`)

### 1.1 New value types (`computed.rs`)

```rust
/// `text-decoration-line`. A bitset so underline+overline can combine.
/// `NONE` is the empty set. Stored as a small `u8` wrapper (no external dep).
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct TextDecorationLine(u8);

impl TextDecorationLine {
    pub const NONE: TextDecorationLine = TextDecorationLine(0);
    pub const UNDERLINE: TextDecorationLine = TextDecorationLine(1);
    pub const OVERLINE: TextDecorationLine = TextDecorationLine(2);
    pub const LINE_THROUGH: TextDecorationLine = TextDecorationLine(4);

    pub fn contains(self, f: TextDecorationLine) -> bool { self.0 & f.0 != 0 }
    pub fn insert(&mut self, f: TextDecorationLine) { self.0 |= f.0; }
    pub fn is_none(self) -> bool { self.0 == 0 }
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ListStyleType {
    Disc,
    Circle,
    Square,
    Decimal,
    None,
}

/// Only `Outside` is supported in M1 but the enum is modelled for forward use.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ListStylePosition {
    Outside,
}
```

### 1.2 New `ComputedStyle` fields

Add to the struct (after the text/font block):

```rust
    // text decoration (M1)
    pub text_decoration_line: TextDecorationLine,

    // list (M1)
    pub list_style_type: ListStyleType,
    pub list_style_position: ListStylePosition,
```

Initial values in `ComputedStyle::initial()`:

```rust
    text_decoration_line: TextDecorationLine::NONE,
    list_style_type: ListStyleType::Disc,   // CSS initial is `disc`
    list_style_position: ListStylePosition::Outside,
```

> Note: the CSS initial of `list-style-type` is `disc`. The UA sheet sets `ul`
> → `disc`, `ol` → `decimal` explicitly (§2); the `disc` initial only matters
> for stray `display:list-item` elements, which we don't generate markers for
> outside `<li>` anyway.

### 1.3 Inheritance (`inherit_from` in `computed.rs`)

`list-style-*` **are inherited** (CSS spec): copy them in `inherit_from`:

```rust
    child.list_style_type = self.list_style_type;
    child.list_style_position = self.list_style_position;
```

`text-decoration-line` is **NOT** inherited and we deliberately do **not**
propagate it to descendant text runs (real CSS draws an ancestor's decoration
across descendant inline text; M1 applies it only to the element's own runs —
deviation noted in §6). So it is left out of `inherit_from` (stays `NONE` on
children unless they set it themselves).

### 1.4 Property parsing (`properties.rs`, new arms in `apply_declaration`)

```rust
        "text-decoration-line" | "text-decoration" => {
            if let Some(line) = text_decoration_of(comps) {
                style.text_decoration_line = line;
            }
        }
        "list-style-type" => {
            if let Some(t) = list_style_type_of(comps) {
                style.list_style_type = t;
            }
        }
        "list-style" => apply_list_style_shorthand(style, comps),
```

Helpers:

```rust
/// Parse `none | [underline || overline || line-through]`. For the
/// `text-decoration` shorthand we ignore any color/style components (M1 always
/// uses the text color + solid). Returns None if no line keyword present.
fn text_decoration_of(comps: &[Component]) -> Option<TextDecorationLine> {
    let mut line = TextDecorationLine::NONE;
    let mut saw_keyword = false;
    for c in comps {
        if let Component::Keyword(k) = c {
            match k.to_ascii_lowercase().as_str() {
                "underline"   => { line.insert(TextDecorationLine::UNDERLINE); saw_keyword = true; }
                "overline"    => { line.insert(TextDecorationLine::OVERLINE); saw_keyword = true; }
                "line-through"=> { line.insert(TextDecorationLine::LINE_THROUGH); saw_keyword = true; }
                "none"        => { saw_keyword = true; } // explicit none → NONE
                _ => {} // solid/color/etc. in the shorthand → ignored
            }
        }
    }
    if saw_keyword { Some(line) } else { None }
}

fn list_style_type_of(comps: &[Component]) -> Option<ListStyleType> {
    match comps {
        [Component::Keyword(k)] => match k.to_ascii_lowercase().as_str() {
            "disc"    => Some(ListStyleType::Disc),
            "circle"  => Some(ListStyleType::Circle),
            "square"  => Some(ListStyleType::Square),
            "decimal" => Some(ListStyleType::Decimal),
            "none"    => Some(ListStyleType::None),
            _ => None,
        },
        _ => None,
    }
}

/// `list-style` shorthand subset: only the `<list-style-type>` keyword is
/// honored; `position`/`image` tokens are ignored (M1). A bare `none` sets the
/// type to `None` (we don't distinguish type-none vs image-none).
fn apply_list_style_shorthand(style: &mut ComputedStyle, comps: &[Component]) {
    for c in comps {
        if let Component::Keyword(k) = c {
            if let Some(t) = list_style_type_of(std::slice::from_ref(c)) {
                style.list_style_type = t;
            } else if k.eq_ignore_ascii_case("outside") || k.eq_ignore_ascii_case("inside") {
                style.list_style_position = ListStylePosition::Outside; // only outside modelled
            }
        }
    }
}
```

Export the new types from `lib.rs`:

```rust
pub use computed::{

    ListStylePosition, ListStyleType, TextAlign, TextDecorationLine,
};
```

### 1.5 UA stylesheet (`ua.rs`)

`<li>` already gets `display:block` from the big block-list rule — keep that
(M1 does **not** introduce a `list-item` display value; markers are driven by
the parent being `<ul>`/`<ol>`, see §3.2). Add list defaults:

```css
ul { list-style-type: disc }

```

(`ul, ol { margin: 16px 0; padding-left: 40px }` already exists — the marker

> `disc` unless author CSS overrides `list-style-type`. Noted in §6.

## 2. Box generation changes (`starfish-layout` boxtree.rs)

### 2.1 inline-block kind

Add a new `BoxKind` variant so layout can treat inline-block specially without
confusing it with a plain `InlineBox`:

```rust
pub enum BoxKind {
    BlockContainer,
    InlineBox,
    InlineBlock,      // NEW: atomic inline; runs block layout internally
    AnonymousBlock,
    TextRun,
    LineBox,
    Marker,           // NEW: list-item marker (see §3.2)
}
```

`is_inline_level` must include both new inline-level kinds:

```rust
pub(crate) fn is_inline_level(&self) -> bool {
    matches!(self.kind, BoxKind::InlineBox | BoxKind::InlineBlock
                       | BoxKind::TextRun | BoxKind::Marker)
}
```

In `build_node`, map the display:

```rust
let kind = match display {
    Display::None => return None,
    Display::Block => BoxKind::BlockContainer,
    Display::Inline => BoxKind::InlineBox,
    Display::InlineBlock => BoxKind::InlineBlock,   // was lumped with Inline
};
```

An `InlineBlock` box keeps its element children built as usual
(`build_children`). It is inline-level (so it joins inline flow / triggers the
anonymous-block rule alongside text), but internally it lays out as a block.

### 2.2 marker box generation

When building an element's children (`build_children`), if the element is a
list item — i.e. its parent tag is `ul`/`ol` **and** the element is `<li>` (we
gate on tag for simplicity, not on a `list-item` display) — and its computed
`list_style_type != None`, prepend a synthetic `Marker` box as the **first
child** of the `<li>`'s box.

Concretely, do it in `build_node` for the element after `build_children`:

```rust
NodeKind::Element(_) => {
    let style = styled.get(id);
    let display = style.map(|s| s.display).unwrap_or(Display::Inline);
    let kind = /* as above */;
    let mut b = LayoutBox::new(kind, BoxStyleRef::Node(id));
    b.children = build_children(doc, styled, id);
    if is_list_item(doc, id) {
        if let Some(marker) = make_marker(doc, styled, id) {
            b.children.insert(0, marker);
        }
    }
    Some(b)
}
```

```rust
/// A node is a list item iff it's <li> whose parent is <ul>/<ol>.
fn is_list_item(doc: &Document, id: NodeId) -> bool {
    doc.tag_name(id) == Some("li")
        && matches!(doc.parent(id).and_then(|p| doc.tag_name(p)), Some("ul") | Some("ol"))
}

/// Build the marker box (text payload), or None if list-style-type:none.
fn make_marker(doc: &Document, styled: &StyledTree, li: NodeId) -> Option<LayoutBox> {
    let st = styled.get(li)?;
    let label = match st.list_style_type {
        ListStyleType::None    => return None,
        ListStyleType::Disc    => "\u{2022}".to_string(), // •
        ListStyleType::Circle  => "\u{25E6}".to_string(), // ◦
        ListStyleType::Square  => "\u{25AA}".to_string(), // ▪
        ListStyleType::Decimal => format!("{}.", ordinal_of(doc, li)),
    };
    let mut m = LayoutBox::new(BoxKind::Marker, BoxStyleRef::Node(li));
    m.text = Some(label);
    Some(m)
}

/// 1-based position of `li` among its <li> element siblings (for <ol>).
/// No `start`/`value`/`counter-reset` support (M1).
fn ordinal_of(doc: &Document, li: NodeId) -> usize {
    let parent = doc.parent(li).unwrap();
    let mut n = 0;
    for c in doc.children(parent) {
        if doc.tag_name(c) == Some("li") {
            n += 1;
            if c == li { break; }
        }
    }
    n
}
```

The marker reuses the `<li>`'s own `ComputedStyle` (font/color), so it paints in
the list item's text color and font. Because it's the **first child**, and `<li>`
content is usually inline, `<li>`'s children become block-or-inline as before;
the marker is inline-level so it participates in the same inline flow as the item
text — but we position it in the gutter at layout time (§3.2), not as a normal
in-flow word.

## 3. Layout

### 3.1 inline-block as an atomic inline (`inline.rs` + new helper in `block.rs`)

Today `collect_words` flattens `InlineBox` children into words and ignores
anything else. inline-block must instead be measured as **one atomic item** of a
fixed width/height and placed like an over-wide word.

**Step A — lay out the inline-block's own block first.** Before inline flow runs
for a container, each `InlineBlock` descendant needs its intrinsic size. We do
this lazily inside `layout_inline` when we encounter one. Add an atomic-item
representation alongside words:

```rust
enum InlineItem {
    Word(CollectedWord),
    Atomic {                 // an inline-block fragment
        boxptr: usize,       // index into a side Vec of laid-out boxes
        width: f32,          // margin-box width (advance on the line)
        height: f32,         // margin-box height (line-height contribution)
        baseline: f32,       // distance origin.y→baseline; M1: = height (bottom-align)
        space_before: bool,
    },
}
```

`collect_words` becomes `collect_items`: on `BoxKind::InlineBlock` it does **not**
recurse for words; instead it:

1. Clones the inline-block sub-box and calls `layout_inline_block(&mut subbox, cb, styled, m)`
   (a thin wrapper that runs block layout with the current container's content
   width as the containing block), then
2. reads its `dimensions.margin_box()` for `width`/`height`, pushes an `Atomic`
   item, and stashes the laid-out box in a side `Vec<LayoutBox>`.

```rust
/// Run block layout on an inline-block sub-box to get its used size. Its content
/// origin is fixed up later when it's committed to a line.
pub(crate) fn layout_inline_block(
    b: &mut LayoutBox,
    cb: Dimensions,
    styled: &StyledTree,
    m: &dyn TextMeasurer,
) {
    // Reuse the block path. `cb.content.width` is the inline container's content
    // width; height starts at 0 so the running-height trick works.
    layout_block(b, cb, styled, m);
}
```

> Width rule (M1, §6): `layout_block`'s existing width algorithm already gives
> *explicit width if set, else fill the containing block*. We accept that — **no
> shrink-to-fit / min-content sizing**. So an inline-block with no `width` fills
> the line (and thus always wraps to its own line); with `width:100px` it's
> 100px wide. This is the simple rule the milestone asks for.

**Step B — line breaking treats an `Atomic` like a word.** In the greedy loop in
`layout_inline`, an `Atomic` advances `cursor_x` by its `width` (plus
`space_before` space), wraps when `cursor_x + space_w + width > avail`, and
contributes its `height` to the line-height max:

```rust
let line_h = match item {
    InlineItem::Word(_) => used_line_height(font_size, lh),
    InlineItem::Atomic { height, .. } => *height, // margin-box height sets line height
};
```

**Step C — commit to a `LineBox`.** A `Word` becomes a `TextRun` fragment as
today. An `Atomic` becomes the stashed laid-out box, **re-offset** so its
margin-box's top-left sits at `(origin.x + offset + x, origin.y + line_y)`.
Because the sub-box was laid out at a provisional origin, we translate the whole
subtree by the delta:

```rust
fn translate_box(b: &mut LayoutBox, dx: f32, dy: f32) {
    b.dimensions.content.x += dx;
    b.dimensions.content.y += dy;
    for c in &mut b.children { translate_box(c, dx, dy); }
}
```

Baseline: M1 bottom-aligns — the inline-block's bottom margin edge sits on the
line's text baseline area; concretely we align its margin-box **top** to the line
top (`origin.y + line_y`) and let the line-height equal the tallest item. This is
"keep simple: bottom-align baseline" from the brief — a single inline-block on a
line just sets the line height to its own height; mixed with text the text shares
the same line top. (Exact baseline alignment is a §6 non-goal.)

`layout_inline` still returns the total height of all lines (now accounting for
atomic-item heights via the per-line max), which the block uses as its content
height.

### 3.2 list marker positioning (`inline.rs`)

A `<li>` runs inline layout for its content (text). The `Marker` box, inserted
as the first inline-level child, must NOT flow as a normal word in the content
column — it sits in the left **gutter** (the `<ul>`/`<ol>` `padding-left:40px`,
which becomes part of the `<li>`'s content origin offset).

Simplest correct approach for `list-style-position: outside`:

1. In `collect_items`, special-case the leading `Marker` child: pull it out of
   the normal word stream and remember it as `marker: Option<(String, BoxStyleRef)>`.
2. After the content lines are built, place the marker on the **first line**, at
   an x **left of** the content origin: `x = -marker_width - GUTTER_GAP`
   (relative to the `<li>` content origin), i.e. it renders into the parent's
   padding-left gutter. `GUTTER_GAP ≈ 0.5em` keeps it off the text.
3. The marker's `y` = first line's `y`, width = measured advance, height = first
   line's line-height. Add it as a `TextRun`-rendered fragment of the first
   `LineBox` (kind stays `Marker` for paint, but it carries `text` + dimensions
   like a `TextRun`).

```rust
// after building `line_boxes`, if a marker exists and there is ≥1 line:
if let Some((label, sref)) = marker {
    let weight = ...; // from <li> style
    let mw = m.measure(&label, font_size, weight);
    let gap = 0.5 * font_size;
    let mut frag = LayoutBox::new(BoxKind::Marker, sref);
    frag.text = Some(label);
    frag.dimensions.content = Rect {
        x: origin.x - mw - gap,   // into the gutter, left of content
        y: line_boxes[0].dimensions.content.y,
        width: mw,
        height: line_boxes[0].dimensions.content.height,
    };
    line_boxes[0].children.insert(0, frag);
}
```

Edge: an empty `<li>` (no content → no lines). M1: skip the marker (no line to
hang it on). Acceptable — empty list items are rare. (Alternative of
synthesizing a one-line-high empty `LineBox` is a §6 non-goal.)

`<li>` whose content is itself block-level (e.g. `<li><p>…`) runs the block path,
not inline. M1 limitation: the marker (an inline-level first child) would be
wrapped into an anonymous block with no text beside it; to keep this simple we
restrict marker placement to the **inline** content path. If an `<li>` has block
children, its marker rides on the first inline line of the first inline
descendant only when that descendant is laid out inline. For M1's test corpus
(`<li>text`) the inline path always applies. Noted in §6.

## 4. Paint (`starfish-paint` display.rs)

### 4.1 text-decoration lines

In `emit_text`, after pushing the `GlyphRun`, emit decoration fill-rects when the
text run's style has `text_decoration_line != NONE`. The run's own
`BoxStyleRef::Node(parent_elem)` carries the element's computed style (which has
the decoration), so `b.style(styled)` already returns the right value.

```rust
fn emit_text(b, styled, fonts, out) {
    let style = ...;
    let text = ...;            // unchanged glyph-run emission
    let c = b.dimensions().content;
    let lm = fonts.line_metrics(style.font_size, style.font_weight);
    // ... push GlyphRun ...

    let deco = style.text_decoration_line;
    if !deco.is_none() {
        let width = c.width;                      // run advance width
        let thickness = (style.font_size / 16.0).max(1.0);
        let color = style.color;                  // decoration color = text color
        let baseline = c.y + lm.ascent;
        let mut line = |y: f32| out.push(PaintCmd::FillRect {
            rect: Rect { x: c.x, y, width, height: thickness },
            color,
        });
        if deco.contains(TextDecorationLine::UNDERLINE) {
            line(baseline + 1.0);                 // just below baseline
        }
        if deco.contains(TextDecorationLine::LINE_THROUGH) {
            line(baseline - lm.ascent * 0.3);     // ~middle / x-height
        }
        if deco.contains(TextDecorationLine::OVERLINE) {
            line(c.y);                            // top of the content box
        }
    }
}
```

Order note: decoration rects are pushed **after** the glyph run for that run.
Underline/overline don't overlap glyph ink meaningfully; line-through sitting on
top of glyphs is the correct visual (it strikes through). Good enough for M1.

The `Marker` box (§3.2/§4.2) carries `text` but is *not* a `TextRun`, so it never
hits `emit_text`'s decoration path — markers are never decorated. Correct.

### 4.2 marker painting

`Marker` fragments carry a `text` payload and absolute dimensions just like a
`TextRun`. Route them through the same glyph-run emission:

```rust
fn paint_box(b, styled, fonts, out) {
    match b.kind() {
        BoxKind::TextRun | BoxKind::Marker => emit_text(b, styled, fonts, out),
        _ => { emit_background(b, styled, out); emit_borders(b, styled, out); }
    }
    for child in b.children() { paint_box(child, styled, fonts, out); }
}
```

But markers must NOT get text-decoration (the `<li>` could have e.g. `underline`
inherited). Guard: only run the decoration block in `emit_text` for
`b.kind() == BoxKind::TextRun`. The bullet/number then paints as plain text in
the `<li>`'s color/font/size via the existing glyph path. Since the disc/circle/
square chars (`•◦▪`) exist in DejaVu Sans, they rasterize directly — no special
shape drawing needed.

### 4.3 inline-block painting

inline-block sub-boxes are committed into `LineBox` children as ordinary
`BoxKind::InlineBlock` / `BlockContainer` / `TextRun` boxes with **absolute**
coordinates (translated in §3.1 Step C). The existing recursive `paint_box`
walks into them and paints their background/border/text correctly. The only
addition: `paint_box`'s `_ => { emit_background; emit_borders }` already handles
`InlineBlock` (it's not `TextRun`), so the inline-block's own bg/border paint,
then its children recurse. **No new paint code for inline-block beyond letting
the walk descend** (which it already does). Verify the display-list walk reaches
fragments nested inside `LineBox`es — it does, via `b.children()`.

## 5. Data-flow summary

```
style:  apply_declaration → text_decoration_line / list_style_type / list_style_position
        inherit_from copies list-style-* (not text-decoration-line)
        UA: ul→disc, ol→decimal

boxtree: Display::InlineBlock → BoxKind::InlineBlock (inline-level, own block layout)
         <li> under <ul>/<ol> → prepend BoxKind::Marker first child (•/◦/▪/"N.")

block:  layout_inline_block = layout_block on the sub-box (used w/h via margin_box)

inline: collect_items → Word | Atomic(inline-block, pre-laid-out)
        greedy wrap: atomic advances by margin-box width, sets line height by its height
        commit: translate atomic sub-box to (line x, line y)
        marker: pulled out of word stream, hung at x = origin.x − mw − 0.5em on line 0

paint:  emit_text: TextRun → GlyphRun + (if decorated) FillRects (under/over/through)
        Marker → GlyphRun only (no decoration)
        InlineBlock/its children → normal recursive bg/border/text walk
```

## 6. Edge cases & non-goals (deliberate deviations)

- **text-decoration**: solid single line only; no `dashed`/`wavy`/`double`, no
  decoration **color**/**style** (always text color, always solid). **No
  inheritance/propagation to descendant inline text** — only the element's own
  text runs are decorated (real CSS draws an ancestor's decoration across
  descendants). Combined lines (e.g. `underline overline`) ARE supported via the
  bitset.
- **list markers**: only `disc`/`circle`/`square`/`decimal`/`none` + `outside`.
  No `list-style-image`, no `inside` rendering, no `lower-roman`/`upper-alpha`/…,
  no `start`/`value`/`counter-reset`/`counter()`. Nested `<ul>` does NOT cycle
  marker glyphs by depth (always the computed `list-style-type`). Marker only on
  `<li>` whose parent is `<ul>`/`<ol>` (no generic `display:list-item`). Marker
  hangs on the first **inline** line; `<li>` with block-only content + empty
  `<li>` get no marker (rare; acceptable).
- **inline-block**: width = explicit `width` else **fills the containing block**

  margin-box top aligned to line top, line height = tallest item (bottom-align

  inline-block follow the existing block rules (indefinite → auto).
- No change to margin collapsing, floats, positioning (later milestones).
