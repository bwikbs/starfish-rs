# E7-M3 — Table layout design note

Scope: add **CSS table layout** as a fourth parallel layout mode (alongside
block/inline, flex, and grid). `display: table` (+ `inline-table`) makes a table
container; `table-row` / `table-cell` / `table-row-group` build the internal
structure; a **pragmatic auto column-width algorithm** sizes columns, row heights
come from cell content, `border-collapse: separate` with `border-spacing` adds
gaps between/around cells, and basic `colspan`/`rowspan` let a cell occupy
multiple grid slots. The HTML `<table>/<tr>/<td>/<th>/<thead>/<tbody>/<tfoot>`
elements get their table displays from the UA stylesheet. Touches
`starfish-style` (new `Display` variants + `border-spacing`/`border-collapse`
props + UA rules) and `starfish-layout` (a new `layout_table` path). **Paint
needs no changes** (table/row/cell boxes are ordinary `BlockContainer`s with
absolute coords; their backgrounds + borders paint via the existing walk).

Guiding rule (project CLAUDE.md "Simplicity First"): the **minimum correct**
table for common cases. The table grid placement directly mirrors grid's
occupancy-grid auto-placement (`grid.rs::place_items`); column sizing is a
single-pass auto/fixed approximation; cell layout reuses `layout_block` exactly
as grid items do. `border-collapse: collapse`, `table-layout: fixed` precision,
captions / `<col>` / `<colgroup>` advanced sizing, and `vertical-align`
middle/bottom in cells are **deferred** (§5). Deviations called out in §5.

This note is pinned to the **real** current APIs (E2..E6 + grid E5-M1/M2 landed).
Verified shapes the design relies on:

- `starfish-style`: `ComputedStyle` is a plain public-field struct built by
  `ComputedStyle::initial()` and mutated by `apply_declaration(style, decl, ctx)`
  (a big `match decl.name.as_str()` in `properties.rs`). `Display::{Block, Inline,
  InlineBlock, Flex, InlineFlex, Grid, InlineGrid, None}` (computed.rs:16). The UA
  sheet is a single CSS string parsed at startup (`ua.rs::UA_CSS`). `Length::{Px,
  Percent, Auto}`. `as_display` (properties.rs:814) maps keywords → `Display`.
  Length-pair parsing pattern: `apply_gap_shorthand` (properties.rs:974) collects
  1-2 lengths exactly like `border-spacing` needs. `as_length`/`set_len`/`set_px`
  (properties.rs:375/401/431) and `as_color` (properties.rs:451) are reusable.
  `inherit_from` (computed.rs:581) copies only the inherited set. Types
  re-exported from `lib.rs:18`.
- `starfish-layout`: `BoxKind::{BlockContainer, InlineBox, InlineBlock,
  AnonymousBlock, TextRun, LineBox, Marker, Image}` (boxtree.rs:23). `LayoutBox {
  kind, style: BoxStyleRef, text, dimensions: Dimensions, children }`.
  `BoxStyleRef::{Node(NodeId), Anonymous(NodeId), Generated{..}}`;
  `style_of(styled, b)` (boxtree.rs:432) resolves a box's `ComputedStyle`,
  falling back to `initial()` for `Anonymous`. `layout_block(b, containing,
  styled, doc, m, images, floats)` (block.rs:30) does width → position →
  **dispatch** → height; it **already** dispatches to `flex::layout_flex` and
  `grid::layout_grid` by `display` (block.rs:42-52). `resolve(len, cb_width) ->
  Option<f32>` / `resolve_or_zero` (block.rs:15/24). `translate_box(b, dx, dy)`
  (inline.rs, `pub(crate)`) shifts a subtree. `is_normal_flow(&style)` /
  `is_out_of_flow` (boxtree.rs). `Dimensions { content: Rect, padding, border,
  margin: EdgeSizes }` with `padding_box()/border_box()/margin_box()`. `mod` list
  in lib.rs: `block, boxtree, dimensions, flex, float, grid, inline, measure` —
  **add `table`**.
- `starfish-dom`: `doc.get_attribute(id, name) -> Option<&str>` (lib.rs:276) for
  `colspan`/`rowspan`; `doc.tag_name`, `doc.children`, `doc.parent`, `doc.kind`.
- `starfish-paint`: `role()` (display.rs:91) reclassifies only
  `BlockContainer|InlineBlock|InlineBox`; a block-level table is a
  `BlockContainer`, inline-table an `InlineBlock` — both paint in the in-flow
  pass. `emit_box_decorations` paints bg + border for any element box from its
  `dimensions` + style (display.rs:294+). **No paint change.**

The **grid** module (`crates/layout/src/grid.rs`, `docs/design/E5-M1.md`) is the
structural template: a new layout function dispatched from `layout_block`, an
occupancy grid for cell placement (`place_items`), sizing tracks (columns/rows),
laying out each cell via `layout_block` into a computed area rect, positioning via
`translate_box`, and returning the container's content height. Table mirrors this
closely, with table-specific structure walking (§2) and a simpler column
algorithm (§3).

## 1. Style additions (`starfish-style`)

### 1.1 New `Display` variants (`computed.rs`)

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Display {
    Block,
    Inline,
    InlineBlock,
    Flex,
    InlineFlex,
    Grid,
    InlineGrid,
    Table,          // NEW: block-level table container
    InlineTable,    // NEW: atomic-inline table container
    TableRowGroup,  // NEW: thead / tbody / tfoot (all map here)
    TableRow,       // NEW: tr
    TableCell,      // NEW: td / th
    None,
}
```

`TableColumn` / `TableColumnGroup` / `TableCaption` / `TableHeaderGroup` /
`TableFooterGroup` are **deferred** (§5): `<col>`/`<colgroup>` get
`display:table-column`/`table-column-group` semantics that M3 does not size from
(no column-defined widths); `<caption>` is laid out as a normal block above the
table only if we add it (deferred — a `<caption>` in M3 keeps `display:block` from
the UA `block` rule and is simply skipped by the table walk, see §2.5). We
deliberately do **not** add those variants to keep the match arms small; the
common `table/row/cell/row-group` set covers the roadmap.

`InlineTable` is the cheap path (mirrors `InlineFlex`/`InlineGrid`): box
generation maps it to `BoxKind::InlineBlock` (an atomic inline) and
`layout_block`'s dispatch picks the table algorithm by display.

`TableRowGroup` / `TableRow` / `TableCell` are **internal-table display types**.
Their generated boxes are `BoxKind::BlockContainer` (they are block-level
structural boxes); the table algorithm reads their `display` while walking the
table subtree (§2) and never lays them out via `layout_block_children` — the table
algorithm positions cells directly. A row/row-group/cell that somehow appears
**outside** a table (no table ancestor running `layout_table`) would fall through
`layout_block` and be laid out as a plain block (its `display` is not flex/grid/
table-container, so it takes the default `layout_block_children` path). That is an
acceptable degenerate rendering (CSS would wrap it in an anonymous table; we don't
— §5).

> `table { border-spacing: 2px }`, which is the browser default authors see. We
> keep the **field** initial at `0` and let the UA rule supply `2px` — matching
> how every other UA default works in this codebase (no special-casing).

`PartialEq` on `ComputedStyle` derives unchanged (`(f32,f32)` and the new enum are
`PartialEq`).

### 1.3 Inheritance (`inherit_from`)

`border-spacing` and `border-collapse` **are inherited** in CSS (they are
inherited table properties so authors can set them once on the table and have
cells/rows see them). Add both to `inherit_from` (computed.rs:581):

```rust
    child.border_spacing = self.border_spacing;
    child.border_collapse = self.border_collapse;
```

This matters because the table algorithm reads `border_spacing` from the **table
container's** own style (§3), but inheritance keeps the value consistent if a
descendant ever needs it; more importantly it matches CSS so a `table { border-
spacing: 4px }` rule is observed on the table element itself (the table reads its
own computed value, which the UA/author rule sets directly). The inheritance is
cheap and spec-correct.

Helpers (mirror `apply_gap_shorthand` at properties.rs:974 and the `*_of`
keyword pattern):

```rust
/// `border-spacing: <length> [<length>]`. One value → both axes; two → (h, v).
/// `auto`/percent are invalid here → ignored. Reuses `as_px_with`.
fn apply_border_spacing(style: &mut ComputedStyle, comps: &[Component], em_basis: f32, rem: f32) {
    let mut vals = Vec::with_capacity(2);
    for c in comps {
        if let Some(px) = as_px_with(std::slice::from_ref(c), em_basis, rem) {
            vals.push(px.max(0.0));
        }
    }
    match vals.as_slice() {
        [h] => style.border_spacing = (*h, *h),
        [h, v, ..] => style.border_spacing = (*h, *v),
        [] => {}
    }
}

fn border_collapse_of(comps: &[Component]) -> Option<BorderCollapse> {
    match comps {
        [Component::Keyword(k)] => match k.to_ascii_lowercase().as_str() {
            "separate" => Some(BorderCollapse::Separate),
            "collapse" => Some(BorderCollapse::Collapse), // stored; treated as separate (§5)
            _ => None,
        },
        _ => None,
    }
}
```

Export from `lib.rs:18` (`pub use computed::{…}`): add `BorderCollapse`. (The
`(f32,f32)` border-spacing needs no exported type.)

## 2. Box generation / anonymous table fixup (`boxtree.rs`)

A table container is a **BlockContainer-like box laid out by the table
algorithm**, mirroring flex/grid. No new `BoxKind`. The internal structure
(row-group / row / cell) is preserved in the box tree as ordinary
`BlockContainer` children; the table algorithm (§3) walks that subtree by reading
each descendant's `display`.

### 2.1 `build_node` display match

`build_node` (boxtree.rs:222) gains arms:

```rust
                Display::Table => BoxKind::BlockContainer,        // block-level table
                Display::InlineTable => BoxKind::InlineBlock,     // atomic-inline table
                Display::TableRowGroup => BoxKind::BlockContainer,
                Display::TableRow => BoxKind::BlockContainer,
                Display::TableCell => BoxKind::BlockContainer,    // a cell is a block container
```

A `TableCell` box is an ordinary `BlockContainer`: its children are built and
wrapped by the normal `build_children` path (so a cell's mixed inline/block
content gets the usual anonymous-block treatment and lays out via
`layout_block_children` when the table algorithm calls `layout_block` on it).
Row-group and row boxes are structural; the table walk reaches through them to the
cells and never lays them out as blocks (their `content` height is set by the
table algorithm so paint draws their bg/border at the right extent — §3.7).

### 2.2 No flexify on table children

Table containers do **not** run `flexify_children`. The `matches!(display,
Flex|InlineFlex|Grid|InlineGrid)` guard (boxtree.rs:247) is left **as-is** — table
displays are excluded. Table children keep their natural box kinds (the
`build_children` anonymous-block rule still runs on each cell's content, which is
what we want). The table's own direct children are typically row-groups/rows
(block-level `BlockContainer`s from the UA displays), so the standard
`wrap_anonymous_blocks` is a no-op on them.

### 2.3 The table grid walk (where fixup happens — in the layout pass, not boxtree)

For **simplicity** (CLAUDE.md), we do the anonymous-table fixup **pragmatically
during the table layout walk** (§3.1), not by synthesizing anonymous boxes in
`boxtree`. The walk collects rows and cells by reading `display`, tolerating
malformed structure:

- **Rows**: descend the table's children. A child with `display:table-row-group`
  (or any wrapper that is not itself a row/cell) is descended into to find its
  `table-row` children. A direct `display:table-row` child of the table is a row
  with no explicit row-group (treated as if in an anonymous row-group — we just
  collect it). This handles the common `<table><tr>…` (no `<tbody>`) authoring,
  the standard `<table><tbody><tr>…`, and `<thead>/<tbody>/<tfoot>` (each a
  row-group; rows collected in document order).
- **Cells**: within each collected row, its `display:table-cell` children are the
  cells. Non-cell in-flow content directly inside a row (e.g. stray text or a
  `<div>`) is, for M3, **skipped** (not wrapped in an anonymous cell) — a
  documented simplification (§5). The common malformed case we **do** handle is
  "rows directly under the table with no row-group", because that is ubiquitous
  HTML.
- **Cells directly under a table or row-group with no row** (e.g.
  `<div style="display:table"><div style="display:table-cell">`): pragmatically,
  if a table/row-group has direct `table-cell` children and no `table-row`
  children, treat **all such direct cells as one anonymous row** (§5; common in
  hand-written `display:table` CSS layouts). Implemented as: when collecting rows,
  if a container yields zero rows but has direct cells, emit one synthetic row
  whose cells are those direct cells.

This walk lives in `table.rs` as `collect_rows(&[LayoutBox], styled) ->
Vec<Row>` where `Row` holds the indices/refs of its cells (§3.1). It is the
table analogue of grid's "items are the container's children" — except a table's
items (cells) are **nested two levels deep** (table → row-group? → row → cell),
so the walk flattens that nesting into a `Vec<Row>` of `Vec<Cell>`.

> Why fixup-at-layout instead of synthesizing anonymous boxes in boxtree:
> synthesizing anonymous `table-row-group`/`table-row` boxes (the full CSS
> anonymous-table algorithm) is significant machinery for little gain in a
> one-shot renderer. Collecting by `display` during the walk handles the same
> common cases with far less code (Simplicity First). The cost: row-group/row
> **boxes** that the author *did* author still paint their bg/border (good — they
> are real boxes in the tree, sized in §3.7); synthetic/anonymous rows have no box
> to paint (acceptable — anonymous boxes are transparent anyway).

## 3. Table layout algorithm (`table.rs`, new module)

New module `crates/layout/src/table.rs`, added to `lib.rs`'s `mod` list. The
container's width/position are already resolved by `layout_block` before
`layout_table` is called, so `content.x/y/width` are set. The algorithm phases:
**(A) walk → rows×cells with colspan/rowspan; (B) build the cell occupancy grid →
column index per cell; (C) size columns; (D) size rows (lay each cell out at its
column width, read height); (E) position cells + size row/row-group boxes.**

### 3.1 Collect structure

```rust
/// One placed cell: its grid position (0-based, end-exclusive) + the child index
/// path to the cell box. `cells` are indexed by a path because cells live nested
/// under rows/row-groups in `b.children`; we store the flattened access route.
struct Cell {
    /// Mutable access route into the table box tree: (row-group child idx OR
    /// None, row child idx, cell child idx). Simpler: resolve to a `&mut LayoutBox`
    /// via a flat index list collected up front (see note).
    path: CellPath,
    col_start: usize,
    col_end: usize,   // col_start + colspan
    row_start: usize,
    row_end: usize,   // row_start + rowspan
    style: ComputedStyle,
}

struct Row {
    /// Index of the row's box in the table tree (for sizing its box, §3.7).
    box_path: RowPath,
    cells: Vec<usize>, // indices into the `Vec<Cell>`
}
```

> **Access-route pragmatics.** Grid items are direct children of the container, so
> grid indexes `children[idx]`. Table cells are 2-3 levels deep. The simplest
> implementation that avoids borrow-checker pain: **flatten the cell boxes into a
> `Vec<&mut LayoutBox>` (or `Vec<*mut>` / index path) once** by walking the table
> subtree, recording for each cell its owning row index and the row's owning
> row-group. Concretely: `std::mem::take(&mut b.children)` (like grid does at
> grid.rs:201), walk the taken `children` tree collecting `(rowgroup_i, row_i,
> cell_i)` index triples and the cell's `style`, build placement, then index back
> into the taken tree mutably by triple to lay out + translate each cell, and
> finally restore `b.children`. A small `cell_mut(&mut children, &CellPath) ->
> &mut LayoutBox` helper resolves a triple. This keeps a single owned tree and
> mutable access without `unsafe`.

Walk (`collect_rows`): for each table child, match `style_of(child).display`:
- `TableRowGroup` → for each of its children that is `TableRow`, push a `Row`
  (its cells = that row's `TableCell` children). If the row-group has direct
  `TableCell` children and no rows, push one synthetic row of those cells (§2.3).
- `TableRow` → push a `Row` directly (cells = its `TableCell` children).
- `TableCell` directly under the table (no row) → accumulate into a pending
  synthetic row; flush it as one row (§2.3).
- anything else (e.g. a `caption` block, stray text) → skip (§5).

Out-of-flow cells/rows (float/abs on a cell — unusual) are skipped via
`is_normal_flow` and handled by the existing float/abs passes, matching grid.

### 3.2 Column count + colspan/rowspan placement (occupancy grid)

This is the **same occupancy-grid technique** as `grid::place_items`
(grid.rs:391), specialized to row-by-row left-to-right cell flow:

- `colspan` = `doc.get_attribute(cell_node, "colspan")` parsed as a positive
  integer (clamp `≥1`, cap at e.g. 1000; default 1). Likewise `rowspan` (default
  1; `rowspan=0` → 1 in M3, no "span to end of group"). Read via the cell's
  `BoxStyleRef::node()` → `doc.get_attribute`.
- Build the grid **row by row**: maintain `occupied: Vec<Vec<bool>>` grown on
  demand (identical helper to grid's `ensure_row`/`cell_free`). For each row `r`
  (0-based over the collected `Vec<Row>`), maintain a column cursor `c = 0`; for
  each cell in document order within the row:
  - advance `c` past any cell already occupied by a `rowspan` from an earlier row
    (`while occupied[r][c] { c += 1 }`);
  - place the cell at `col_start = c`, `col_end = c + colspan`,
    `row_start = r`, `row_end = r + rowspan`;
  - mark `occupied[rr][cc] = true` for `rr in row_start..row_end`,
    `cc in col_start..col_end` (growing rows for rowspan);
  - advance `c = col_end`.
- **Column count** = `max` over all cells of `col_end` (= the widest row's summed
  colspans, accounting for rowspan overhang). This is the standard "number of
  columns = max row width" rule.

This handles colspan (a cell occupies N contiguous columns), rowspan (subsequent
rows skip the occupied slots — exactly the `while occupied` advance), and ragged
rows (rows with fewer cells than the column count leave trailing empty slots).

### 3.3 Column widths (the pragmatic auto/fixed algorithm)

The CSS auto table algorithm computes per-column min/max content widths and
distributes; M3 implements a **correct-for-common-cases approximation** (roadmap
permits; min/max precision deferred — §5):

1. **Per-column preferred width.** For each column `j`, gather the
   **single-column** cells in it (`col_end == col_start + 1`, i.e. `colspan == 1`,
   placed at `col_start == j`). Measure each such cell's **preferred content
   width** = `layout_block` the cell at a generous width and read its content
   extent (reuse grid's `measure_item_width`/`intrinsic_width` technique,
   grid.rs:606-635: lay the cell out at `container_w`, take the rightmost leaf
   fragment). A cell with an explicit `width: Npx` uses `N` directly (the
   `Length::Px` short-circuit already in `measure_item_width`). Column preferred
   width `pref[j]` = `max` over its single-column cells (0 if none).
2. **Spanning cells (`colspan > 1`).** For M3, a multi-column cell's preferred
   width is **distributed equally** across its spanned columns only if it would
   otherwise exceed their current sum: for each spanning cell, if
   `cell_pref > Σ pref[col_start..col_end] + interior h-spacing`, bump each
   spanned column's `pref` up evenly so the sum matches (a single pass, no
   iteration). This is the pragmatic "spanning cells widen narrow columns"
   behavior; precise min/max distribution is deferred (§5).
3. **Table used width.** Let `H = border_spacing.0` (horizontal). The structural
   horizontal spacing total in the separate model is `H * (cols + 1)` (spacing on
   both outer edges + between every pair of columns). The **content width
   available to columns** is the table content box minus that spacing:
   `avail = table_content_w - H * (cols + 1)`.
   - If the table has an **explicit/definite width** (`self_style.width` resolves;
     the block width algorithm already set `b.dimensions.content.width`):
     `avail` is fixed. Distribute: start from `pref[j]`; if `Σ pref < avail`,
     **grow** columns to fill (proportional to `pref`, or equally if all `pref`
     are 0); if `Σ pref > avail`, **shrink** proportionally (clamp `≥ 0`). This is
     the "table width set → scale columns" rule.
   - If the table width is **auto** (the common `<table>` with no width): the
     block width algorithm gave the table the **full containing width** (auto
     block fills its container — block.rs:139). Two acceptable M3 behaviors:
     **(a)** treat that as a definite width and distribute (table fills its
     container, columns share it proportionally to `pref`) — simplest, matches a
     stretched layout; **(b)** shrink-to-fit the table to `Σ pref + spacing`. CSS
     auto tables are shrink-to-fit, but `layout_block` already filled the width.
     **M3 picks (a) when content underflows is undesirable**: use
     `used_table_content_w = min(table_content_w, Σ pref + H*(cols+1))` to
     shrink-to-fit, then set `col[j] = pref[j]` (no growth) — i.e. **the table is
     as wide as its columns need, up to its container**. Recommended M3 rule:
     **shrink-to-fit auto tables** (`col[j] = pref[j]`, table content width =
     `Σ col + H*(cols+1)`, re-pin `b.dimensions.content.width`), and **distribute
     for definite-width tables** (grow/shrink columns to fill the set width). This
     matches common `<table>` rendering (columns hug content) while honoring an
     explicit `width`. Percentage column/table widths resolve against the
     container (basic — §5).
4. **Percentage table width** resolves via the existing block width algorithm
   (already definite by the time `layout_table` runs). Percentage **column**
   widths (a cell `width:30%`) are resolved against the table content width in
   step 1 (treated as a preferred width); precise percentage column distribution
   is deferred (§5).

Result: a `Vec<f32> col_w` of length `cols`, and a definite table content width
(re-pinned for auto tables).

> Reuse: steps 1-2 lean entirely on grid's `measure_item_width` +
> `intrinsic_width` (lay a cell out via `layout_block`, take its max content
> extent). Copy/adapt those two small fns into `table.rs` (or hoist them to a
> shared `measure.rs` helper — impl's choice; copying ~30 lines is acceptable and
> surgical). The `Length::Px` width short-circuit gives exact arithmetic for
> tests that set explicit cell widths.

### 3.4 Column x-offsets

With horizontal spacing `H` and column widths `col_w`, the **left edge of column
j** (table-content-relative) is:

```
x_off[0] = H                                  // outer spacing before column 0
x_off[j] = x_off[j-1] + col_w[j-1] + H        // spacing between columns
```

A cell at `col_start` has `cell_x = content_x + x_off[col_start]`, and a cell
spanning `col_start..col_end` has
`cell_w = Σ col_w[col_start..col_end] + H*(col_end - col_start - 1)` (the spanned
column widths + interior spacings, **not** the outer spacing). A helper mirrors
grid's `Tracks::span_extent`/`line_offset`.

### 3.5 Row heights

For each row `r`, lay out each of its cells at the cell's **column-span width**
(`cell_w` from §3.4) via `layout_block` and read the cell's natural content
height (reuse grid's `measure_item_height`, grid.rs:638). A cell's **outer
height** = content height + its vertical border+padding (cells have no margins in
the table model — margins on cells are ignored, §5). `row_h[r]` = `max` over the
row's **single-row** cells (`rowspan == 1`) of their outer height (0 if none — an
empty row collapses, plus any explicit row `height`).

**rowspan distribution (pragmatic).** A cell with `rowspan > 1` spans
`row_start..row_end`. Its height requirement is **assigned to its last spanned
row** (§5): after computing single-row `row_h`, for each spanning cell, if
`cell_outer_h > Σ row_h[row_start..row_end] + V*(rowspan-1)` (V = vertical
spacing), bump `row_h[row_end - 1]` up by the shortfall. This guarantees the
spanning cell fits, without the precise CSS rowspan height-distribution
(deferred). Explicit row `height` (a `<tr style="height:..">`) sets a floor on
`row_h[r]` via `resolve(row_style.height, …)`.

### 3.6 Row y-offsets

With vertical spacing `V = border_spacing.1`:

```
y_off[0] = V
y_off[r] = y_off[r-1] + row_h[r-1] + V
```

Cell at `row_start`: `cell_y = content_y + y_off[row_start]`; a rowspan cell's
height = `Σ row_h[row_start..row_end] + V*(row_end - row_start - 1)`.

### 3.7 Lay out + position cells, size structural boxes

For each cell (iterate the flattened cell list, indexing back into the taken
`children` tree by its path — §3.1 note):

```
cell_x = content_x + x_off[col_start]
cell_y = content_y + y_off[row_start]
cell_w = span_extent_cols(col_start, col_end)   // §3.4
cell_h = span_extent_rows(row_start, row_end)    // §3.6
```

Lay the cell out as a block into its rect (a cell is a block container; its
content flows normally), then **fill the cell** (cells stretch to their column
width and row height — CSS cells fill their slot):

```rust
let cb = Dimensions {
    content: Rect { x: cell_x, y: cell_y, width: cell_w, height: 0.0 },
    ..Dimensions::default()
};
let mut floats = FloatContext::default(); // each cell establishes its own BFC
layout_block(cell, cb, styled, doc, m, images, &mut floats);
// Cells have no margins; pin content size so the border box fills the slot.
let hbp = cell.dimensions.border.left + cell.dimensions.border.right
        + cell.dimensions.padding.left + cell.dimensions.padding.right;
let vbp = cell.dimensions.border.top + cell.dimensions.border.bottom
        + cell.dimensions.padding.top + cell.dimensions.padding.bottom;
cell.dimensions.margin = EdgeSizes::default();            // table cells ignore margins
cell.dimensions.content.width  = (cell_w - hbp).max(0.0);
cell.dimensions.content.height = (cell_h - vbp).max(0.0); // vertical-align: top (content at top)
// Position the cell's border-box top-left at (cell_x, cell_y).
let cur = cell.dimensions.border_box();
translate_box(cell, cell_x - cur.x, cell_y - cur.y);
```

`vertical-align: top` is implicit: content was laid out from the top of the
content box and the box is grown downward to `cell_h`. Middle/bottom are deferred
(§5).

**Structural boxes (rows / row-groups).** After cells are positioned, set each
**row box's** `dimensions.content` to span its columns and its row height, and
each **row-group box's** to span all columns and its rows, so their backgrounds +
borders paint at the right extent (a `<tr style="background:..">` or
`<tbody>` bg is common). Concretely:

```
row r:    content = Rect { x: content_x, y: content_y + y_off[r],
                           width: total_columns_width, height: row_h[r] }
rowgroup: content = Rect spanning its first..last row's y-range, full table width
```

where `total_columns_width = Σ col_w + H*(cols-1)` (the columns + interior
spacing; outer edge spacing sits outside the rows, like real tables). This is a
small bookkeeping pass; if the impl wants to keep it minimal, it may set only the
**cell** geometry and leave row/row-group boxes at their default (zero) size —
then row/row-group backgrounds won't paint (acceptable M3 simplification, but
sizing them is cheap and the test plan asserts a `<tr>` background, so **size the
row boxes**; row-group sizing is optional). Recommend: size **rows** (cheap,
tested); row-groups optional.

### 3.8 Container height returned

```
table_content_h = V (top edge) + Σ row_h + V*(rows-1) (interior) + V (bottom edge)
                = Σ row_h + V*(rows + 1)
```

`layout_table` returns this; `layout_block` stores it as `content.height` and
`calculate_block_height` lets an explicit `height` on the table override. Inline
tables return the same; their atom height feeds the line box.

### 3.9 Entry signature + body outline

Mirrors `layout_grid` (grid.rs:182) exactly:

```rust
/// Lay out a table container's rows/cells. The container's width/position are
/// already resolved by `layout_block`. Returns the table's content-box height.
/// Cells are positioned absolutely via `translate_box`; the table content width
/// may be re-pinned (shrink-to-fit auto tables, §3.3).
pub(crate) fn layout_table(
    b: &mut LayoutBox,
    containing: Dimensions,
    self_style: &ComputedStyle,
    styled: &StyledTree,
    doc: &Document,
    m: &dyn TextMeasurer,
    images: &dyn ImageSource,
) -> f32;
```

Body:

```rust
let content_x = b.dimensions.content.x;
let content_y = b.dimensions.content.y;
let table_content_w = b.dimensions.content.width;
let (h_space, v_space) = self_style.border_spacing;
let explicit_h = resolve(self_style.height, containing.content.height);

let mut children = std::mem::take(&mut b.children);
// 1. collect rows×cells (§3.1) + colspan/rowspan
// 2. occupancy-grid placement → per-cell col/row ranges + column count (§3.2)
// 3. size columns → col_w + re-pinned table width (§3.3)
// 4. column x-offsets (§3.4)
// 5. size rows → row_h (lay cells out at their col-span width) (§3.5)
// 6. row y-offsets (§3.6)
// 7. lay out + position each cell; size row boxes (§3.7)
b.children = children;

let rows_h = row_h.iter().sum::<f32>() + v_space * (rows as f32 + 1.0);
explicit_h.unwrap_or(rows_h)
```

### 4.3 Paint (`starfish-paint`)

**No paint changes.** A block-level table is a `BlockContainer`, an inline-table
an `InlineBlock` — both paint in the in-flow pass via `role()` (display.rs:91).
Cells, rows, and row-groups are `BlockContainer`s with **absolute** content
coordinates assigned in §3.7; `build_display_list`/`paint_subtree` descend into
them and `emit_box_decorations` (display.rs:294) draws each box's background +
border from its `dimensions` + style — so **cell backgrounds + cell/table borders
paint via the existing walk** (the common table visuals). Row backgrounds paint
because §3.7 sizes the row boxes. Cells are never out of flow, so no float/
positioned diversion. **Confirmed: no change needed.** (`border-collapse:
collapse` shared-border painting is what would need paint work — deferred, §5.)

## 5. Edge cases & explicit non-goals

Handled:
- `display:table` (block-level) + `display:inline-table` (atomic inline).
- `display:table-row-group` (thead/tbody/tfoot), `table-row`, `table-cell`.
- `<table>/<tr>/<td>/<th>/<thead>/<tbody>/<tfoot>` via UA displays;
  `th` bold + centered.
- Pragmatic anonymous fixup: rows directly under a table (no row-group); cells
  directly under a table/row-group with no row (one synthetic row).
- Auto column widths (per-column max preferred content width); explicit cell
  `width:Npx`; spanning-cell column widening.
- Definite table `width` → columns distributed (grow/shrink to fill); auto table
  → shrink-to-fit columns.
- Row heights from cell content; explicit `<tr height>` floor.
- `border-collapse: separate` with `border-spacing` (1 or 2 lengths): spacing
  between columns, between rows, and around the table edge.
- `colspan` (cell spans N columns; width = spanned cols + interior h-spacing) +
  `rowspan` (cell spans M rows; subsequent rows skip occupied slots via the
  occupancy grid; height assigned-to-last-row).
- Cell backgrounds + cell/table/row borders paint (existing walk).
- Nested tables, table-in-grid/flex, grid/flex-in-cell via recursive
  `layout_block`.

Explicit **non-goals / simplifications** for M3:
- **`border-collapse: collapse`** → parsed but treated as `separate` (no shared-
  border resolution / no border painting changes). Deferred.
- **`table-layout: fixed`** → not parsed; the auto approximation is used always.
  Min/max content-width precision (the full CSS auto algorithm) is deferred — M3
  uses single-pass preferred widths.
- **Captions / `<col>` / `<colgroup>`** → not sized. `<caption>` keeps
  `display:block` and is skipped by the table walk (rendered, if at all, as a
  detached block; recommend simply ignoring it). Column-defined widths from
  `<col width>` are not honored. Deferred.
- **`vertical-align` in cells** → `top` only (content at the cell's top). middle/
  bottom deferred.
- **Non-cell content directly inside a row** → skipped (no anonymous-cell wrap).
- **`rowspan` height distribution** → assigned to the last spanned row, not
  distributed proportionally across spanned rows.
- **`rowspan=0` / `colspan=0`** ("span to end") → clamped to 1.
- **Cell margins** → ignored (table cells don't take margins in the CSS model;
  M3 zeroes them).
- **Percentage table/column widths** → basic (resolved against the container /
  table content width as preferred widths); precise percentage distribution
  deferred.
- **Empty cells / empty rows / a single cell / a single-row table** → handled
  (zero-content columns size to 0, empty rows collapse; no panic).
- **Out-of-flow cells/rows** (float/abs on a cell) → skipped by the table walk
  (`is_normal_flow`), handled by the float/abs passes; a loosely-supported,
  uncommon combination.
- **`empty-cells` property** → not implemented (cells always paint their bg/
  border; CSS `empty-cells:hide` deferred).

### style
- `display: table` → `Display::Table`; `inline-table` → `Display::InlineTable`;

- `border-spacing: 4px` → `(4.0, 4.0)`; `border-spacing: 4px 8px` → `(4.0, 8.0)`.
- `border-collapse: collapse` → `BorderCollapse::Collapse` (stored); default

- UA: a `<table>` element computes `display == Table`, `border_spacing ==
  (2.0,2.0)` (UA `2px`); a `<th>` computes `font_weight == 700` (bold) and
  `text_align == Center`; `<tr>` → `TableRow`; `<td>` → `TableCell`; `<tbody>` →
  `TableRowGroup`.
- inheritance: a cell inside a `table{border-spacing:6px}` sees the table's
  computed `border_spacing` on the table element (the table reads its own value);
  a descendant inherits `border_spacing == (6,6)`.

### layout — basic grid
- **2×2 table, `border-spacing:0`.** Two rows of two cells, each cell content
  width 50, height 20 (e.g. text at per=10, "abcde"). Columns each 50, rows each
  20 → cell rects: (0,0)50×20, (50,0)50×20, (0,20)50×20, (50,20)50×20. Table
  content height = 40.
- **column sizes to its widest cell.** Col 0 cells "ab"(20) and "abcdef"(60) →
  col 0 width 60; the narrow cell stretches to 60.
- **border-spacing adds gaps.** Same 2×2 with `border-spacing: 10px` → cell0 at
  (10,10), cell1 at (10+50+10=70, 10), row1 at y = 10+20+10 = 40; table content
  height = 20+20 + 10*3 = 70; table content width (auto, shrink-to-fit) =
  50+50 + 10*3 = 130.
- **border-spacing 2 lengths.** `border-spacing: 4px 12px` → horizontal gaps use
  4, vertical use 12 (assert a cell's x uses 4-spacing, y uses 12-spacing).

### layout — spans
- **colspan=2.** Row 0: one cell `colspan:2`; row 1: two cells (each width 40).

  row 1 sits below the row-0 cell, col-0 slot in row 1 is occupied (skipped).

- **ragged rows.** Row 0 has 3 cells, row 1 has 2 → column count 3; row 1's
