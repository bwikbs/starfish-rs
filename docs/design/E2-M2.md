# E2-M2 — float / clear + positioning (relative / absolute / fixed) design note

Scope: extend the existing block + inline flow layout (`starfish-layout`, with
small additions to `starfish-style` and `starfish-paint`) to support:

1. **`float: left | right`** — a floated box is taken out of normal flow,
   shrink-to-fit width (or explicit width), placed at the left/right edge of its
   containing block's content, stacking against earlier floats. Subsequent
   in-flow block boxes' **line boxes are shortened** to flow around the float.
2. **`clear: left | right | both`** — a block with clear drops below the relevant
   floats.
3. **`position: relative`** — box stays in normal flow (reserves its space) but
   is *painted* offset by `top`/`left`/`right`/`bottom`.
4. **`position: absolute`** — out of flow; sized + positioned relative to the
   **nearest positioned ancestor**'s padding box (or the initial containing block
   / viewport if none).
5. **`position: fixed`** — like absolute but relative to the viewport.

Guiding rule (project CLAUDE.md "Simplicity First"): the **minimum correct**
subset; floats and positioning are complex, so the subset is tight but gets the
common cases right. Deliberate deviations are called out in §6.

This note is pinned to the **real** current APIs read from the source (the M4
note `docs/design/M4-layout.md` + E2-M1 already landed). The relevant existing
shapes:

- `starfish-style`: `ComputedStyle` is a plain struct of public fields built by
  `ComputedStyle::initial()` and mutated by `apply_declaration(style, decl, ctx)`
  (a big `match decl.name.as_str()`); `Length::{Px(f32), Percent(f32), Auto}`;
  `inherit_from` copies the inherited set; values re-exported from `lib.rs`.
- `starfish-layout`: `BoxKind::{BlockContainer, InlineBox, InlineBlock,
  AnonymousBlock, TextRun, LineBox, Marker}`; `LayoutBox { kind, style:
  BoxStyleRef, text, dimensions: Dimensions, children: Vec<LayoutBox> }`,
  `is_inline_level()`. `layout_block(b, containing, styled, m)` does
  width→position→children→height; `layout_block_children` either stacks block
  children with the running-`content.height` cursor trick or calls
  `layout_inline(b, styled, m) -> f32`. `Dimensions { content: Rect, padding,
  border, margin: EdgeSizes }` with `padding_box()/border_box()/margin_box()`.
- `starfish-paint`: `build_display_list(root, styled, fonts) -> Vec<PaintCmd>`
  via `paint_box` pre-order; `PaintCmd::{FillRect, GlyphRun}`.

## 2. Box generation (`boxtree.rs`)

**Keep out-of-flow boxes in the tree.** Do not collect them into side lists at
generation time. The box tree is built exactly as today; layout reads
`position`/`float` from the box's `ComputedStyle` and diverts boxes from normal
vertical stacking. This keeps box generation untouched and confines the new logic
to the layout pass.

Two small structural points:

- **No new `BoxKind`.** A floated or absolutely-positioned element is still a
  `BlockContainer` (it has `display:block` after the float/abs blockification —
  see below). The box's *style* tells layout it is out of flow.
- **Float/abs blockification.** CSS says a floated or absolutely-positioned
  element computes `display` to a block-level value. For M2 we do the minimal
  thing: in `build_node`, when an element is out of flow, force its `BoxKind` to
  `BlockContainer` even if its `display` is `Inline`/`InlineBlock`:

  ```rust
  NodeKind::Element(_) => {
      let style = styled.get(id);
      let display = style.map(|s| s.display).unwrap_or(Display::Inline);
      let out_of_flow = style.map(is_out_of_flow).unwrap_or(false);
      let kind = match display {
          Display::None => return None,
          _ if out_of_flow => BoxKind::BlockContainer, // float/abs/fixed → block
          Display::Block => BoxKind::BlockContainer,
          Display::Inline => BoxKind::InlineBox,
          Display::InlineBlock => BoxKind::InlineBlock,
      };
      // ...rest unchanged (build_children, marker)...
  }
  ```

  ```rust
  /// A box is out of flow if it floats or is absolutely/fixed positioned.
  pub(crate) fn is_out_of_flow(s: &ComputedStyle) -> bool {
      s.float != Float::None
          || matches!(s.position, Position::Absolute | Position::Fixed)
  }
  ```

  (`position:absolute` wins over `float` per CSS — `is_out_of_flow` only needs
  "either", and §4 resolves the precedence: an absolutely-positioned box ignores
  its `float`.)

- **`is_inline_level` must treat an out-of-flow box as NOT inline-level** so it
  never joins a line and never forces an anonymous block. But `is_inline_level`
  is a method on `LayoutBox` and has no style access. Resolution: out-of-flow
  boxes are already forced to `BoxKind::BlockContainer` above, and
  `is_inline_level()` returns false for `BlockContainer`. So a floated/abs box is
  block-level in the tree and the anonymous-block rule (§2.3 of M4) treats it as
  a block sibling — which is what we want for diversion. **No change to
  `is_inline_level`.**

  > Consequence/limitation: a float that appears *between inline text* (e.g.
  > `<p>text<span style="float:left">F</span>more</p>`) becomes a block sibling
  > and triggers anonymous-block wrapping of the surrounding text rather than
  > sitting inline at its source position. The common authoring pattern — a float
  > as a block-level child of a block container, with following block/inline
  > siblings flowing around it — works correctly. Noted §6.

## 3. Float layout

### 3.1 The float context

Floats are tracked per **block formatting context** (BFC). For M2 the root
block container establishes the BFC and we thread **one** `FloatContext` through
the block-layout recursion (we do not create nested BFCs for `overflow` etc. —
§6). The context records placed floats as absolute-page-space rects tagged by
side:

```rust
#[derive(Debug, Clone, Copy)]
enum FloatSide { Left, Right }

#[derive(Debug, Clone, Copy)]
struct PlacedFloat {
    side: FloatSide,
    /// The float's margin-box rect in absolute page space.
    rect: Rect,
}

#[derive(Debug, Default)]
pub(crate) struct FloatContext {
    floats: Vec<PlacedFloat>,
}
```

Queries the context answers, all in **absolute page coordinates**:

```rust
impl FloatContext {
    /// Left inset at vertical band [y, y+height): how far in from `cb_left` the
    /// content must start because of left floats overlapping that band.
    fn left_offset(&self, y: f32, height: f32, cb_left: f32) -> f32 { /* … */ }

    /// Right inset at [y, y+height): how far in from `cb_right` (right edge of
    /// the containing block content) the content must stop.
    fn right_offset(&self, y: f32, height: f32, cb_right: f32) -> f32 { /* … */ }

    /// Lowest bottom edge among floats of the given side(s) — used for `clear`
    /// and for float drop-down. `None` of the requested side → returns `y_floor`.
    fn clearance_y(&self, sides: ClearSides, y_floor: f32) -> f32 { /* … */ }

    /// Record a placed float.
    fn add(&mut self, side: FloatSide, rect: Rect) { self.floats.push(PlacedFloat{side,rect}); }
}
```

A float "overlaps" a band `[y, y+h)` when `f.rect.y < y+h && f.rect.bottom > y`.
`left_offset` = `max(0, max over overlapping left floats of (f.rect.right -
cb_left))`. `right_offset` symmetric. A zero-height band (`h == 0`, used when
querying at a single y before a line height is known) treats overlap as
`f.rect.y <= y && f.rect.bottom > y`.

### 3.2 Threading the context through block layout

`layout_block` and `layout_block_children` gain a `&mut FloatContext` parameter.
`layout_inline` gains a **read-only** `&FloatContext` (it only queries; it never
places floats). The public `layout()` entry creates a fresh `FloatContext` for
the root and passes it down:

```rust
pub(crate) fn layout_block(
    b: &mut LayoutBox,
    containing: Dimensions,
    styled: &StyledTree,
    m: &dyn TextMeasurer,
    floats: &mut FloatContext,
);
```

(`layout_inline_block` for atomic inline-blocks lays out in an *independent*
sub-context — it establishes its own BFC — so it gets a fresh `FloatContext`
internally and does not see the outer floats. Minimal and matches CSS: an
inline-block is a BFC root.)

### 3.3 Placing a float

In `layout_block_children`, when iterating block-level children, **before**
laying out a child check its style. A child is a **float** when
`style.float != None && !matches!(style.position, Absolute|Fixed)` (abs wins,
§4). For a float child, instead of the normal stack step:

1. **Resolve width.** Run the normal width algorithm but with the M2
   shrink-to-fit rule:
   - explicit `width` (px/%) → that width.
   - `width: auto` → **shrink-to-fit**, approximated for M2 as
     `min(max_content, available)`, where `available` is the containing block's
     content width and `max_content` is the float's preferred content width. We
     approximate `max_content` by laying the float's content out at the available
     width first and taking the widest line / child extent. A simpler accepted
     fallback (§6): lay out at the available width and use the resulting used
     content width capped at available — for the common case of a float with an
     explicit width this branch never triggers, and for `<div style="float:left">
     short text</div>` the cap-at-available result is "fills available", which is
     acceptable but wide. **Recommended M2 rule:** require an explicit width OR a
     replaced/`inline-block`-ish content for a tight float; otherwise fill
     available. Tests use explicit widths. Noted §6.
2. **Compute the float's margin-box size** by laying it out (reuse
   `layout_block` on the float sub-box with a provisional origin; this fills its
   `dimensions` including height). Floats do not collapse margins (§6).
3. **Find the placement y and x.** Start at the current normal-flow y-cursor
   `cur_y` (the running `content.y` for the next in-flow child) — a float may not
   be higher than the content that precedes it. Let `fw = margin_box().width`,
   `fh = margin_box().height`, `cb_left = containing.content.x`, `cb_right =
   cb_left + containing.content.width`.
   - For `Left`: candidate `x = cb_left + ctx.left_offset(y, fh, cb_left)`. The
     float fits beside existing floats iff
     `x + fw <= cb_right - ctx.right_offset(y, fh, cb_right)`. If it does not
     fit, **drop down**: advance `y` to the smallest float bottom edge below the
     current `y` (via `clearance_y`) and retry. (Guaranteed to terminate: at a y
     below all floats both offsets are 0 and the float fits, or it's wider than
     the CB and is placed at `cb_left` overflowing — accepted.)
   - For `Right`: place its margin-box right edge at
     `cb_right - ctx.right_offset(y, fh, cb_right)`; `x = right_edge - fw`. Same
     drop-down rule against the left offset.
4. **Translate the laid-out float sub-box** so its margin-box top-left sits at
   `(x, y)` (reuse the existing `translate_box` helper from `inline.rs`, made
   `pub(crate)`).
5. **Record** `ctx.add(side, float.margin_box())`.
6. The float **does not advance** the normal-flow y-cursor (`content.height` is
   unchanged for the parent's running stack) — it is out of flow. The parent's
   auto height, however, does **not** include floats in M2 (no
   "floats establish/extend block height"): a parent whose only content is a
   float collapses to zero height. This is the well-known float-collapse, and
   matching it (rather than clearfix) is the simple correct M2 behavior. Noted
   §6.

The float sub-box stays a child of its parent in the tree (kept in document
order). After it is laid out and translated, we leave it in `b.children` so paint
walks it; we just skip the "grow `content.height`" step for it.

### 3.4 In-flow block boxes flowing around floats

When a normal in-flow block child is laid out, its **content position and width
are unchanged** at the block level (block boxes still span the full CB content
width per CSS — only their *line boxes* are shortened). The float interaction
happens in `layout_inline`:

`layout_inline(b, styled, m, floats)` now receives `&FloatContext`. The greedy
line breaker, for each line, queries the float context at the line's current
absolute y to get the available horizontal band:

- Before starting a line at relative `line_y` (absolute `origin.y + line_y`),
  with a provisional line height (we use the container's used line-height as the
  band height for the query; refined to the actual line height once known is a
  §6 nicety — for M2 the provisional band height is fine):
  - `left_inset  = floats.left_offset(abs_y, band_h, origin.x)`
  - `right_inset = floats.right_offset(abs_y, band_h, origin.x + avail)`
  - `line_start_x = origin.x + left_inset` (relative start = `left_inset`)
  - `line_avail   = avail - left_inset - right_inset`
- Words are placed from `left_inset` (relative) rightward and wrap when
  `cursor_x + space + w > left_inset + line_avail`. Each line independently
  recomputes the band, so once `line_y` passes the float's bottom the inset
  returns to 0 and subsequent lines are full width — **producing the
  text-wraps-around-float effect.**
- The `LineBox`'s `content.x` becomes `origin.x + left_inset` and its
  `content.width` becomes `line_avail`; fragment x positions are offset by the
  line start. text-align offset (existing code) uses `line_avail` as the
  available width instead of the full `avail`.

Concretely, the line-build loop changes from a single `avail`/`origin.x` to a
**per-line** `(line_start_rel, line_avail)` pair recomputed from `floats` at the
band of the line being filled. The `Collector` and item collection are unchanged;
only the placement/break thresholds and the committed `LineBox`/fragment x become
band-aware.

### 3.5 clear

`clear` applies to a **block-level in-flow** box. In `layout_block_children`,
before computing a non-float child's position, if its `style.clear != None`,
compute clearance:

```rust
let sides = match style.clear {
    Clear::Left => ClearSides::Left,
    Clear::Right => ClearSides::Right,
    Clear::Both => ClearSides::Both,
    Clear::None => ClearSides::None,
};
let floor = floats.clearance_y(sides, cur_abs_y); // ≥ cur_abs_y
// raise the running y-cursor so this child starts at/below `floor`
```

Implementation detail with the running-`content.height` cursor: the cursor is a
*relative* running height added to `containing.content.y`. To enforce clearance
we bump the running height so that `containing.content.y + running_height >=
floor` *before* the child's `calculate_block_position` runs. The cleared child's
top margin is then applied on top (M2 does not collapse clearance with the
following margin — §6). After clearing, the child stacks normally and its own
in-flow following siblings continue from its bottom.

`clearance_y(sides, y_floor)` = `max(y_floor, max bottom edge of floats whose
side is in `sides`)`. `Both` considers all floats.

## 4. Positioned layout (relative / absolute / fixed)

### 4.1 `position: relative`

Relative boxes **stay in normal flow** — they are laid out exactly as today
(reserving their space; siblings unaffected). The offset is applied as a
**post-layout translation of the box and its subtree**, after the box's own
children are laid out and after it has taken its in-flow slot:

In `layout_block`, after `calculate_block_height`, if
`style.position == Relative`, compute the offset and translate:

```rust
if style.position == Position::Relative {
    let cbw = containing.content.width;
    let cbh = containing.content.height; // for top/bottom % (indefinite → 0, §6)
    let dx = rel_offset(style.left, style.right, cbw);
    let dy = rel_offset(style.top, style.bottom, cbh);
    translate_box(b, dx, dy); // moves paint position only; flow already fixed
}
```

```rust
/// CSS relative offset: `left` wins if set, else `-right`, else 0. (% of CB
/// width for left/right; of CB height for top/bottom — indefinite → 0, §6.)
fn rel_offset(start: Length, end: Length, basis: f32) -> f32 {
    match (resolve(start, basis), resolve(end, basis)) {
        (Some(s), _) => s,        // `left`/`top` set → use it
        (None, Some(e)) => -e,    // only `right`/`bottom` → shift the other way
        (None, None) => 0.0,
    }
}
```

Because relative translation happens **after** the parent has already accumulated
this child's in-flow margin-box height (the parent used the pre-translation
geometry for stacking), siblings are unmoved — exactly the CSS "reserves its
space, painted offset" semantics. The translation moves the whole subtree
(children move with the parent), which is correct.

### 4.2 `position: absolute` / `fixed` — two-phase approach

Absolute and fixed boxes are **skipped in normal flow** (they do not advance the
parent's y-cursor and do not contribute to auto height). They are laid out in a
**second pass** once their containing block's geometry is known.

This is the cleanest M2 structure (vs. trying to lay them out inline during the
first pass, which would need the containing block's final size that isn't known
yet). Two phases:

**Phase 1 — normal flow.** During the first `layout` traversal:
- An abs/fixed box is detected in `layout_block_children`
  (`matches!(style.position, Absolute|Fixed)`). It is **not** laid out and
  **not** stacked — left in `b.children` with zeroed dimensions, to be filled in
  phase 2.
- While traversing, maintain a **stack of positioned ancestors' padding boxes**
  so phase 2 can resolve each abs box's containing block. We record, for every
  abs/fixed box, the rect of its containing block at the moment it is
  encountered. Simplest implementation: a side `Vec` of "abs work items"
  collected during phase 1:

  ```rust
  struct AbsItem {
      /// Path to the box in the tree, OR a raw pointer-free index. In practice
      /// we record it by walking again in phase 2 (see below) rather than
      /// storing &mut — the layout owns the tree.
      cb_rect: Rect,    // containing block's padding-box (abs) or viewport (fixed)
      is_fixed: bool,
  }
  ```

  Because we own the tree and Rust makes storing `&mut LayoutBox` across the
  recursion awkward, the pragmatic M2 implementation is: **phase 2 re-walks the
  tree** carrying a stack of containing-block rects, and lays out each abs/fixed
  box it finds. The "nearest positioned ancestor" is tracked by the walk itself
  (see below), so no separately-stored path is needed.

**Phase 2 — `layout_absolutes(root, viewport, styled, m)`.** A recursive walk
that threads the current **containing-block rect** for absolutely-positioned
descendants:

```rust
fn layout_absolutes(
    b: &mut LayoutBox,
    abs_cb: Rect,       // padding box of nearest positioned ancestor (abs CB)
    viewport: Rect,     // initial containing block / viewport (fixed CB)
    styled: &StyledTree,
    m: &dyn TextMeasurer,
) {
    let style = style_of(styled, b);

    // If THIS box is abs/fixed, lay it out against the right CB now.
    if matches!(style.position, Position::Absolute) {
        layout_abs_box(b, abs_cb, styled, m);
    } else if matches!(style.position, Position::Fixed) {
        layout_abs_box(b, viewport, styled, m);
    }

    // Determine the CB this box provides to its abs descendants: its own
    // padding box iff it is positioned (relative/absolute/fixed), else inherit.
    let child_abs_cb = if style.position != Position::Static {
        b.dimensions.padding_box()
    } else {
        abs_cb
    };
    for c in &mut b.children {
        layout_absolutes(c, child_abs_cb, viewport, styled, m);
    }
}
```

Subtlety — order: a box must be laid out (so its `padding_box()` is valid) before
we descend to provide it as a CB. For a **positioned** box, `layout_abs_box`
above fills its geometry first; for a **relative/static** box its geometry was
already filled in phase 1 (relative was even translated). So `child_abs_cb` is
always valid when we recurse. A `relative` box was translated in phase 1, so its
`padding_box()` reflects the translated position — correct (abs children of a
relatively-positioned box follow it).

Entry wiring in `layout()`:
```rust
let viewport_rect = Rect { x: 0.0, y: 0.0, width: viewport_width,
                           height: root.dimensions.content.height };
layout_absolutes(&mut root, viewport_rect, viewport_rect, styled, measurer);
```
The initial `abs_cb` and `fixed` CB are both the viewport (an abs box with no
positioned ancestor uses the ICB = viewport). The viewport height is taken as the
root content height after phase 1 (the page grows with content; §6 — abs/fixed
`bottom`/`%`-height against the viewport use this definite value).

### 4.3 `layout_abs_box` — sizing + positioning

```rust
fn layout_abs_box(b: &mut LayoutBox, cb: Rect, styled: &StyledTree, m: &dyn TextMeasurer) {
    let s = style_of(styled, b);
    let cbw = cb.width;

    // --- width ---
    // explicit width → used; else if both left & right set → stretch between
    // them; else shrink-to-fit (M2: approximate as min(max_content, cbw); the
    // simple accepted fallback is "lay out at cbw, take used content width").
    let used_w = match resolve(s.width, cbw) {
        Some(w) => w,
        None => match (resolve(s.left, cbw), resolve(s.right, cbw)) {
            (Some(l), Some(r)) => (cbw - l - r
                - h_border_padding_margin(&s, cbw)).max(0.0), // stretch
            _ => shrink_to_fit_width(b, cb, styled, m),       // §6 approximation
        },
    };

    // Lay the box's own block out at the resolved width to fill children/height.
    // Build a synthetic containing Dimensions whose content origin is the CB's
    // top-left and content width = used_w, height = 0 (running cursor).
    let containing = Dimensions {
        content: Rect { x: cb.x, y: cb.y, width: used_w, height: 0.0 },
        ..Dimensions::default()
    };
    let mut local_floats = FloatContext::default(); // abs box is its own BFC
    layout_block(b, containing, styled, m, &mut local_floats);
    // layout_block set width again from `containing`; for abs we override width
    // to `used_w` and recompute margins simply (auto offsets → static-ish, §6).
    b.dimensions.content.width = used_w;

    // --- position ---
    // left/top resolved against the CB padding box; `right`/`bottom` used only if
    // the corresponding start offset is auto. Auto offsets → 0 (static-position
    // approximation, §6). The box is positioned by its MARGIN-box top-left.
    let mb = b.dimensions.margin_box();
    let x = match (resolve(s.left, cbw), resolve(s.right, cbw)) {
        (Some(l), _) => cb.x + l,
        (None, Some(r)) => cb.x + cb.width - r - mb.width,
        (None, None) => cb.x, // static-position approximation
    };
    let y = match (resolve(s.top, cb.height), resolve(s.bottom, cb.height)) {
        (Some(t), _) => cb.y + t,
        (None, Some(b_off)) => cb.y + cb.height - b_off - mb.height,
        (None, None) => cb.y, // static-position approximation
    };
    // Translate so the margin-box top-left lands at (x, y).
    let cur = b.dimensions.margin_box();
    translate_box(b, x - cur.x, y - cur.y);
}
```

`h_border_padding_margin` sums the resolved horizontal border+padding(+non-auto
margins) — small helper. `shrink_to_fit_width` lays the box out at `cbw` and
returns its used content width (the §6 approximation); for tests we always set an
explicit width or both offsets, so this path is exercised lightly.

> Note the abs box runs `layout_block` to size its own descendants and to honor
> an explicit `height`; we then re-pin its width and translate the whole subtree
> into place. Abs descendants of an abs box are handled by phase 2's recursion
> (which provides the abs box's padding box as their CB).

### 4.4 Finding the nearest positioned ancestor / the ICB

Handled entirely by the phase-2 walk's `child_abs_cb` threading (§4.2): the
"nearest positioned ancestor" is the most recent ancestor on the walk whose
`position != Static`, and its **padding box** is what propagates as `abs_cb`.
The **ICB** is the viewport rect, used as the seed `abs_cb` (for abs boxes with
no positioned ancestor) and as the fixed CB everywhere.

## 5. Paint order (`starfish-paint`)

CSS paints, within a stacking context (z-index out of scope, §6), roughly: block
backgrounds/borders → floats → in-flow inline/line content → positioned
descendants — all in tree order within each band. The existing `paint_box` does a
single pre-order walk emitting bg/border then recursing (and text on
`TextRun`/`Marker`). To get out-of-flow boxes painting **on top of** in-flow
content without a full layering rewrite, we split the walk into **ordered
passes** by skipping out-of-flow boxes in the in-flow pass and painting them
afterward.

`build_display_list` becomes:

```rust
pub fn build_display_list(root, styled, fonts) -> Vec<PaintCmd> {
    let mut out = Vec::new();
    // Pass 1: in-flow content (skip floats + abs/fixed subtrees).
    paint_box(root, styled, fonts, &mut out, PaintPass::InFlow);
    // Pass 2: floats (tree order), each as a normal subtree.
    paint_box(root, styled, fonts, &mut out, PaintPass::Floats);
    // Pass 3: positioned boxes (relative/abs/fixed), tree order.
    paint_box(root, styled, fonts, &mut out, PaintPass::Positioned);
    out
}
```

`paint_box(b, …, pass)` walks pre-order but, at each box, decides whether to
**emit + descend normally**, **skip the subtree**, or **emit the subtree and stop
descending for this pass**, based on the box's role and the pass:

- Classify each box via its style: `is_float`, `is_positioned`
  (`position != Static`), else in-flow. (Relative counts as positioned for paint
  so it layers above in-flow siblings — CSS-correct.)
- **InFlow pass:** if a box is a float or positioned → **prune** (don't emit,
  don't descend; it's painted in a later pass). Otherwise emit bg/border/text and
  descend.
- **Floats pass:** when we reach a float box → paint its **whole subtree**
  unconditionally (its own normal in-flow content), then do not descend further
  *for this pass* past it. For non-float boxes, descend looking for floats but do
  not emit them. A positioned box encountered before a float prunes (its floats
  belong to the positioned pass / its own subtree, handled in pass 3).
- **Positioned pass:** when we reach a positioned box → paint its **whole
  subtree** (recursively, which re-runs the three-pass ordering *within* that
  subtree so nested positioned/floats inside it still layer correctly). Don't
  emit non-positioned ancestors.

To keep this genuinely simple and avoid re-deriving stacking inside subtrees, the
recommended M2 implementation is a **single classification + three flat
collections**: walk once, bucket each box into `inflow` / `float` / `positioned`
*entry points* (a box becomes an entry point when its role differs from the
in-flow walk and we stop the in-flow descent there), then emit:
`paint_subtree(inflow_root)`, then each float entry subtree in tree order, then
each positioned entry subtree in tree order. Each `paint_subtree` is the original
recursive `paint_box`, **except** it must itself prune nested out-of-flow entries
so they aren't double-painted (they're painted by the later buckets). Concretely:

```rust
enum Role { InFlow, Float, Positioned }
fn role(b, styled) -> Role { /* positioned > float > inflow */ }

/// Pre-order, collecting out-of-flow subtree roots; emits in-flow boxes only.
fn collect_and_emit_inflow(b, styled, fonts, out, floats: &mut Vec<&LayoutBox>,
                           positioned: &mut Vec<&LayoutBox>) {
    match role(b, styled) {
        Role::Float => { floats.push(b); return; }       // defer whole subtree
        Role::Positioned => { positioned.push(b); return; } // defer whole subtree
        Role::InFlow => {
            emit_self(b, styled, fonts, out);             // bg/border or text
            for c in b.children() {
                collect_and_emit_inflow(c, styled, fonts, out, floats, positioned);
            }
        }
    }
}
```

Then for each deferred subtree root call `collect_and_emit_inflow` again (it
emits that root's in-flow content and re-defers any *nested* out-of-flow boxes,
appending to the same buckets — processed FIFO until drained). Floats bucket is
drained before positioned bucket so positioned content layers on top of floats.
Tree order within each bucket is preserved by the pre-order push order.

This yields the required ordering with **no z-index and no stacking-context
machinery**: in-flow first, then floats, then positioned, each in tree order —
and it cannot regress the existing tests, which have no floats/positioned boxes
(everything is in-flow, so pass 1 paints exactly as before and passes 2/3 are
empty).

> `emit_self` is the existing per-box logic factored out of `paint_box`:
> `TextRun|Marker → emit_text`, else `emit_background + emit_borders`. No change
> to `emit_text`/`emit_background`/`emit_borders`.

## 6. Edge cases & explicit non-goals

Handled:
- `float:left/right` block-level child taken out of flow, placed against the
  side, stacking against earlier floats with drop-down when it doesn't fit.
- In-flow block line boxes shortened around floats (text wraps; full width below).
- `clear:left/right/both` drops a block below the relevant floats.
- `position:relative` reserves space, paints translated (siblings unmoved).
- `position:absolute` sized/positioned against nearest positioned ancestor's
  padding box (ICB/viewport if none); `position:fixed` against the viewport.
- Negative offsets (e.g. `left:-10px`) via the existing signed length parse.

Explicit **non-goals** for M2 (documented limitations):
- **No `z-index` / stacking contexts** — paint order is purely tree order within
  the in-flow → floats → positioned passes (§5).
- **No margin collapsing changes** — clearance does not collapse with the
  following block's top margin; floats do not collapse margins.
- **Float shrink-to-fit simplified** — a width-`auto` float is approximated
  (min(max_content, available) ≈ "fill available" in the simple fallback). Tests
  give floats an explicit width. True min/max-content sizing is out.
- **No float interaction with margins beyond basics** — float margins count in
  its margin-box for placement, but no negative-margin float tricks.
- **No new BFC roots** — one float context for the root BFC; `overflow`,
  `display:flow-root`, abs/inline-block-as-BFC nuances are not modeled (abs boxes
  and inline-blocks do get a fresh independent float context, which is enough).
- **Floats don't extend parent auto height** — a parent containing only floats
  collapses (no clearfix). Following *cleared* content still drops correctly.
- **Abs/fixed auto-offset resolution simplified** — when both the start offset and
  size (or both offsets) are auto, the box is placed at the CB origin (a
  static-position approximation), not the true CSS static position computed from
  where the box would have been in flow.
- **`fixed` == absolute-vs-viewport** — no scrolling, so a fixed box is just
  positioned against the (content-sized) viewport rect; identical machinery to
  absolute with the viewport as CB.
- **Float between inline text** becomes a block sibling (anonymous-block
  wrapping) rather than an inline-anchored float (§2); the common block-level
  float case is correct.
- **`%` for `top`/`bottom`** resolves against the CB height, which for an
  indefinite-height in-flow CB is 0 (relative) — effectively no offset; abs/fixed
  use the definite viewport / positioned-ancestor padding-box height.

## 7. Test plan (concrete)

Layout tests in `crates/layout/src/lib.rs` use the existing `FixedMeasurer`
(`per` px/char) for exact geometry; paint tests in
`crates/paint/src/display.rs` use the real `FontDb`. Style tests in
`crates/style/src/lib.rs`.

### style
- `position: relative|absolute|fixed|static` → the matching `Position` variant;
  bogus keyword → unchanged initial `Static`.
- `float: left|right|none` → `Float`; `clear: both` → `Clear::Both`.
- `top: 10px`, `left: -5px`, `right: 50%`, `bottom: auto` → the right `Length`
  (incl. negative px and percent).
- none of `position`/`float`/`clear`/offsets inherit: child of a
  `position:relative` parent computes `Position::Static`.

### layout — float + wrap
- **Left float shortens following lines.** A `div{float:left;width:W;height:H}`
  followed by a `<p>` of several words: assert the `<p>`'s first `LineBox`(es)
  whose y-band overlaps `[0, H)` have `content.x == p.content.x + W` (start
  shifted right by the float width) and reduced `content.width`; a later line
  with `y >= H` has `content.x == p.content.x` and full width. Word counts per
  line reflect the narrower then wider available width.
- **Right float.** `float:right;width:W` → the float's margin-box right edge sits
  at the CB content right edge; the following paragraph's overlapping lines have
  full `content.x` but `content.width == avail - W`.
- **Float stacking + drop-down.** Two left floats each width `0.6*avail` →
  second cannot fit beside the first, so it drops below (its `content.y >=`
  first float's margin-box bottom).

### layout — clear
- **`clear:both` drops below.** A left float (height H) then a
  `div{clear:both}` sibling → the cleared div's `content.y >=` the float's
  margin-box bottom (not overlapping the float's band). A non-cleared sibling in
  the same position would start at the float's top y (control assertion).

### layout — positioned
- **relative shifts paint only.** `div#a{position:relative;left:20px;top:10px}`
  between two static divs → `a.content.x == base_x + 20`, `a.content.y ==
  base_y + 10`, **and** the following sibling's `content.y` is unchanged vs. the
  no-offset baseline (space reserved).
- **absolute within relative parent.** `#p{position:relative;padding:5px}`
  containing `#c{position:absolute;top:10px;left:15px;width:30px;height:20px}` →
  `c.margin_box().x == p.padding_box().x + 15` and
  `c.margin_box().y == p.padding_box().y + 10`; `c` does **not** advance `p`'s
  in-flow height (a static sibling text sits at the top of `p`).
- **absolute with no positioned ancestor → viewport.** `#c{position:absolute;
  top:0;left:0}` under only static ancestors → `c.margin_box().{x,y} == (0,0)`
  (the ICB origin).
- **fixed at viewport offset.** `#f{position:fixed;top:5px;right:5px;width:20px}`
  → its margin-box right edge `== viewport_width - 5`, top `== 5`, regardless of
  any positioned ancestor.

### paint — ordering
- **float paints above in-flow background, below positioned.** A page with an
  in-flow `div` (background), a `float:left` div (background), and a
  `position:absolute` div (background): assert the float's bg `FillRect` appears
  **after** the in-flow div's bg, and the absolute's bg appears **after** the
  float's bg, in the display list.
- **no regression.** An existing in-flow-only page (e.g. the
  `background_before_border_before_text` corpus) produces the identical display
  list under the new three-pass `build_display_list` (passes 2/3 empty).
