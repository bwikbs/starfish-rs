# E2-M3 — Flexbox layout design note

Scope: add **flexbox** as a parallel layout mode to the existing block + inline
flow. `display: flex` makes an element a flex container; its in-flow children
become flex items laid out along a main axis, with grow/shrink distributing free
space and cross-axis alignment. Touches `starfish-style` (new `Display` variant +
flex properties) and `starfish-layout` (a new `layout_flex` path); **paint needs
no changes** (flex items are ordinary boxes with absolute coords).

Guiding rule (project CLAUDE.md "Simplicity First"): the **minimum correct**
single-line + simple wrapping flex. We correct the common cases (row/column,
grow/shrink/basis, justify, align-items, gap, nesting) and defer intrinsic-sizing
precision, `order`, `align-content`, baseline precision, etc. Deliberate
deviations are called out in §6.

This note is pinned to the **real** current APIs read from the source (E2-M1 and
E2-M2 already landed). The relevant existing shapes:

- `starfish-style`: `ComputedStyle` is a plain struct of public fields built by
  `ComputedStyle::initial()` and mutated by `apply_declaration(style, decl, ctx)`
  (a big `match decl.name.as_str()`); `Length::{Px(f32), Percent(f32), Auto}`;
  `Display::{Block, Inline, InlineBlock, None}`; value enums + parse helpers live
  in `computed.rs`/`properties.rs`; `inherit_from` copies only the inherited set;
  types re-exported from `lib.rs`. `Component::{Keyword(String), Number(f32),
  Dimension{value,unit}, Color, Comma, Str, …}`.
- `starfish-layout`: `BoxKind::{BlockContainer, InlineBox, InlineBlock,
  AnonymousBlock, TextRun, LineBox, Marker}`; `LayoutBox { kind, style:
  BoxStyleRef, text, dimensions: Dimensions, children: Vec<LayoutBox> }`;
  `is_inline_level()`; `style_of(styled, b) -> ComputedStyle`. `layout_block(b,
  containing, styled, m, floats)` does width→position→children→height;
  `layout_block_children` either stacks block children with the running
  `content.height` cursor or calls `layout_inline`. `Dimensions { content: Rect,
  padding, border, margin: EdgeSizes }` with `padding_box()/border_box()/
  margin_box()`. `translate_box(b, dx, dy)` shifts a subtree.
  `TextMeasurer::{measure, line_metrics}`. `layout()` builds the tree, runs
  `layout_block`, then `layout_absolutes` (phase 2).
- `starfish-paint`: `build_display_list(root, styled, fonts)` →
  `paint_subtree` recursion in three role-based passes (in-flow / float /
  positioned). `role()` only reclassifies `BlockContainer|InlineBlock|InlineBox`.

## 1. Style additions (`starfish-style`)

### 1.1 New `Display` variant (`computed.rs`)

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Display {
    Block,
    Inline,
    InlineBlock,
    Flex,        // NEW
    InlineFlex,  // NEW (cheap — see §2)
    None,
}
```

`InlineFlex` is cheap: in box generation it maps to `BoxKind::InlineBlock` (an
atomic inline) **with a flex-layout flag**, so it joins inline flow like an
inline-block but lays its children out via the flex algorithm internally. The
flex algorithm itself does not care whether the container is block-level or
atomic-inline — it just lays out the container's children. See §2.

**`flex` shorthand** (`flex: none | auto | initial | <grow> [<shrink>] [<basis>]`,
and a single number = grow). The spec defaults: when omitted in the explicit
form, `shrink` = 1 and `basis` = 0 (note: the `flex` shorthand's *omitted basis*
is `0`, **not** `auto` — differs from the `flex-basis` longhand default). The
named keywords expand to:
- `none` → `0 0 auto`
- `auto` → `1 1 auto`
- `initial` → `0 1 auto`

```rust
/// `flex` shorthand. Sets flex_grow / flex_shrink / flex_basis together.
fn apply_flex_shorthand(
    style: &mut ComputedStyle,
    comps: &[Component],
    em_basis: f32,
    rem: f32,
) {
    // keyword forms
    if let [Component::Keyword(k)] = comps {
        match k.to_ascii_lowercase().as_str() {
            "none"    => { style.flex_grow = 0.0; style.flex_shrink = 0.0; style.flex_basis = Length::Auto; return; }
            "auto"    => { style.flex_grow = 1.0; style.flex_shrink = 1.0; style.flex_basis = Length::Auto; return; }
            "initial" => { style.flex_grow = 0.0; style.flex_shrink = 1.0; style.flex_basis = Length::Auto; return; }
            _ => {}
        }
    }
    // numeric / length form: collect a grow number, optional shrink number,
    // optional basis length, in any order that parses. Spec defaults when the
    // explicit form is used: shrink=1, basis=0.
    let mut grow: Option<f32> = None;
    let mut shrink: Option<f32> = None;
    let mut basis: Option<Length> = None;
    for c in comps {
        let one = std::slice::from_ref(c);
        if let Some(l) = as_length(one, em_basis, rem) {
            // a length (px/%/em/auto) → basis
            basis = Some(l);
        } else if let Component::Number(n) = c {
            // first number → grow, second → shrink
            if grow.is_none() { grow = Some(*n); }
            else if shrink.is_none() { shrink = Some(*n); }
        }
    }
    if grow.is_some() || shrink.is_some() || basis.is_some() {
        style.flex_grow = grow.unwrap_or(0.0).max(0.0);
        style.flex_shrink = shrink.unwrap_or(1.0).max(0.0);
        style.flex_basis = basis.unwrap_or(Length::Px(0.0)); // omitted basis = 0
    }
}
```

> Note: a single `Component::Number(0.0)` reaching `as_length` returns
> `Length::Px(0.0)` (existing `as_length` treats bare `0` as px). To keep
> `flex: 0` meaning *grow 0* (not basis 0) the loop above checks `Number` for
> grow/shrink **after** trying `as_length`. To avoid `flex: 1` being read as a
> length, special-case: a bare integer/number with no unit is a **grow** value,
> never a basis. So `as_length(one)` must be guarded to only accept
> `Dimension`/`auto` here, not bare `Number`. Concretely the loop tries
> `Number` → grow/shrink **first**, and only treats `Dimension{..}` /
> `auto` keyword as basis. (Impl: split the branch order so `Number` wins.)

**`gap` shorthand** (`gap: <row> [<column>]`; one value sets both):

```rust
fn apply_gap_shorthand(
    style: &mut ComputedStyle,
    comps: &[Component],
    em_basis: f32,
    rem: f32,
) {
    let mut lens = Vec::with_capacity(2);
    for c in comps {
        if let Some(l) = as_length_no_auto(std::slice::from_ref(c), em_basis, rem) {
            lens.push(l);
        }
    }
    match lens.as_slice() {
        [g] => { style.row_gap = *g; style.column_gap = *g; }
        [r, c, ..] => { style.row_gap = *r; style.column_gap = *c; }
        [] => {}
    }
}
```

## 2. Box generation (`boxtree.rs`)

A flex container is a **BlockContainer-like box laid out by the flex algorithm**.
We do **not** add a `BoxKind::FlexContainer` — instead we reuse the existing kinds
and let layout dispatch on the container's `display`:

- `Display::Flex` → `BoxKind::BlockContainer` (block-level box; lays out via
  `layout_flex` instead of `layout_block_children`).
- `Display::InlineFlex` → `BoxKind::InlineBlock` (atomic inline; its internal
  layout uses `layout_flex`). This is the cheap path: inline-flex rides the
  existing inline-block machinery (`layout_inline_block` → `layout_block`), and
  `layout_block` dispatches to flex when the box's display is a flex value.

`build_node`'s display match gains the two arms:

```rust
let kind = match display {
    Display::None => return None,
    _ if out_of_flow => BoxKind::BlockContainer, // float/abs blockify (M2)
    Display::Block => BoxKind::BlockContainer,
    Display::Flex => BoxKind::BlockContainer,      // NEW: block-level flex container
    Display::Inline => BoxKind::InlineBox,
    Display::InlineBlock => BoxKind::InlineBlock,
    Display::InlineFlex => BoxKind::InlineBlock,    // NEW: atomic-inline flex container
};
```

**Flex items.** The container's in-flow children become flex items. Per spec,
flex items are *blockified*: each in-flow child of a flex container computes its
inner `display` to a block-level value, and contiguous runs of text are wrapped
in anonymous flex items. For M3 we keep this **pragmatic**:

- The container's children are built as usual by `build_children`. We then need
  every in-flow child to be a box that `layout_flex` can lay out and size. The
  existing `build_children` already produces `BlockContainer` / `InlineBlock` /
  `InlineBox` / `TextRun` / anonymous boxes.
- **Skip anonymous-block wrapping for flex containers.** `build_children` calls
  `wrap_anonymous_blocks`, which is the block-flow rule. For a flex container we
  instead want each top-level inline-level child (text run / inline box / inline-
  block) to become its own flex item. Simplest correct M3 approach: after
  building the container's children, if the container's display is a flex value,
  run `flexify_children` instead of (the already-applied) anonymous wrapping:
  - Drop pure-whitespace `TextRun` children (between items).
  - Wrap each remaining **inline-level** child (or a maximal run of them) in an
    `AnonymousBlock` so it becomes a block-level flex item that can run block/
    inline layout internally. Block-level children (`BlockContainer`,
    `InlineBlock`) are left as-is, each already a flex item.
  - Out-of-flow children (float / abs / fixed) are **NOT flex items** — they keep
    the M2 behavior (a float/abs child is `BoxKind::BlockContainer` already; the
    flex algorithm in §3 skips them and they are handled by the float/abs passes).

  ```rust
  /// Turn a flex container's raw children into flex items: drop whitespace-only
  /// runs, wrap inline-level runs in anonymous blocks; block-level children pass
  /// through. Out-of-flow children are left in place (skipped by layout_flex).
  fn flexify_children(children: Vec<LayoutBox>, elem: NodeId) -> Vec<LayoutBox> { … }
  ```

  Pragmatic shortcut accepted for M3 (§6): rather than a separate function, we
  may reuse `wrap_anonymous_blocks` — for the common case (a flex container whose
  children are element boxes like `<div>`s, each `display:block`/`inline-block`)
  the children are already separate block-level items and wrapping is a no-op.
  The only case `flexify_children` improves is bare text / `<span>` children
  directly inside the container; those are wrapped so each becomes an item.

- **`is_inline_level` / out-of-flow** classification is unchanged. The flex item
  detection in §3 reads the child's `ComputedStyle` via `style_of` and treats a
  child as a flex item iff `is_normal_flow(&cstyle)` (i.e. not float/abs/fixed).

No change to `BoxKind`, `is_inline_level`, or `LayoutBox`.

## 3. Flex layout algorithm (`layout/src/flex.rs`, new module)

New module `flex.rs` added to `lib.rs`'s `mod` list. The entry:

```rust
/// Lay out a flex container `b` (already width/position-resolved by
/// `layout_block`'s width+position phase) by running the flex algorithm over its
/// in-flow children. Sets each item's dimensions + the container's content
/// height. `floats` is threaded only so an item's own block layout stays float-
/// aware in its sub-context; the flex container itself establishes a new BFC, so
/// in practice items get a fresh float context (matching inline-block, §3.2 M2).
pub(crate) fn layout_flex(
    b: &mut LayoutBox,
    containing: Dimensions,
    self_style: &ComputedStyle,
    styled: &StyledTree,
    m: &dyn TextMeasurer,
) -> f32;   // returns the container's content-box height (main=column or cross)
```

### 3.0 Integration with block dispatch (THE hook)

`layout_block` already runs width → position → children → height. We dispatch on
the container's display **inside `layout_block_children`** (or just before it),
so flex containers reuse the existing width/position resolution (a block-level
flex container's content width is resolved exactly like a block — §4) and only
the *children + height* phase differs:

```rust
// in block.rs, layout_block(), replacing the layout_block_children call:
let style = style_of(styled, b);
calculate_block_width(b, &style, containing);
calculate_block_position(b, &style, containing);
if matches!(style.display, Display::Flex | Display::InlineFlex) {
    let h = flex::layout_flex(b, containing, &style, styled, m);
    b.dimensions.content.height = h;     // auto height = flex content height
    // (explicit height still overrides below via calculate_block_height)
} else {
    layout_block_children(b, &style, containing, styled, m, floats);
}
calculate_block_height(b, &style);   // explicit height wins; else keep flex height
// position:relative translation (M2) unchanged.
```

This makes flex a **parallel layout mode** confined to one function, exactly
mirroring how `layout_block_children` chooses inline vs block. `InlineFlex` works
for free: `layout_inline_block` → `layout_block` → this dispatch picks flex.

### 3.1 Axes

From `flex_direction`:

```text
is_row    = matches!(dir, Row | RowReverse)
is_reverse= matches!(dir, RowReverse | ColumnReverse)
main axis = horizontal if is_row else vertical
cross axis= vertical   if is_row else horizontal
main_gap  = is_row ? column_gap : row_gap     // gap *between items along main*
cross_gap = is_row ? row_gap    : column_gap  // gap *between flex lines*
```

We work in **logical** sizes (`main`, `cross`) and only convert to physical
`x/y/width/height` at the final positioning step (§3.7). A small helper:

```rust
struct Axis { row: bool }                 // row = main is horizontal
impl Axis {
    fn main_size(&self, d: &Dimensions) -> f32 { if self.row { d.margin_box().width } else { d.margin_box().height } }
    fn cross_size(&self, d: &Dimensions) -> f32 { … }
    // etc.
}
```

### 3.2 Container main/cross size (definite sizes the algorithm runs against)

- **Main size of the container's content box** = the available space items are
  distributed in.
  - Row: `containing`-resolved content **width** (already set by
    `calculate_block_width` on `b.dimensions.content.width`). This is definite.
  - Column: the container's **height** if explicit (`style.height` definite),
    else the column main size is content-driven (the sum of item base sizes +
    gaps) — i.e. an auto-height column container grows to fit its items. We use
    `resolve(style.height, containing.content.height)` if definite, else compute
    it from item base sizes (§3.4: `free_space < 0` only when height is definite;
    with auto height, items take their base sizes and the container's main size =
    their total).
- **Cross size of the container's content box**:
  - Row: the container's **height** if explicit, else auto (driven by the tallest
    line — computed after item cross sizes are known, §3.6).
  - Column: the container's content **width** (definite, from
    `calculate_block_width`).

### 3.3 Flex base size + hypothetical main size of each item

For each in-flow item (skip float/abs/fixed children), resolve its **flex base
size** along the main axis:

1. If `flex_basis` is **not** `Auto` → resolve it against the container main size
   (`Px` direct; `Percent` of the container main size; §6 percentage basis
   simplified). This is the base size.
2. If `flex_basis` is `Auto`:
   - If the item has a definite **main-axis size** property set (`width` for row,
     `height` for column, non-auto) → use that resolved value.
   - Else → the item's **content main size**: run the item's own block layout
     once (`layout_block` on a clone/in-place at the container main size as its
     containing width) and read the used main size. For row this is the item's
     used content width (which for an auto-width block fills the container, so for
     M3 we instead use a **measured max-content** approximation: lay the item out
     and take `max(used content width, ...)`; see note). For column it is the
     item's laid-out content height.

> **M3 content-size pragmatics (§6).** Auto-width block items fill their
> container under the existing block width algorithm, which is wrong for a flex
> base size (we want max-content). The pragmatic rule: **prefer explicit sizes.**
> If the item has an explicit main size or a non-auto `flex_basis`, use it
> (exact). If it is auto with text content, lay it out at the container main size
> and use the resulting content extent — acceptable, and tests give items
> explicit `width`/`flex-basis`/`flex` basis so this path is exercised lightly.
> True min/max-content intrinsic sizing is out of scope.

The **hypothetical main size** = base size clamped to the item's `[min, max]`
main size. M3 supports `min-content` as **0** and no `max` unless `max-width`/
`max-height` are added later — so for M3 hypothetical = base size (clamp is a
no-op; min defaults 0). Noted §6.

Each item also gets its **outer main size** = hypothetical main size + the item's
main-axis margin+border+padding (the flex algorithm distributes space over the
*content* sizes but positions by *outer* margin boxes; we track both).

```rust
struct FlexItem<'a> {
    idx: usize,                 // index into the container's children Vec
    style: ComputedStyle,
    base_main: f32,             // flex base (content) main size
    hyp_main: f32,             // clamped base (= base in M3)
    grow: f32, shrink: f32,
    margin_main_start: f32, margin_main_end: f32,   // resolved outer margins (main)
    margin_cross_start: f32, margin_cross_end: f32,
    main_bpm: f32,             // border+padding along main (added to content size)
    cross_size: f32,           // filled in §3.6
    // align_self resolved against the container's align_items
}
```

### 3.4 Collect items into flex lines

- `Nowrap`: **one line** containing all items.
- `Wrap`: greedily fill lines. Start a line; add items while the running
  `sum(outer hypothetical main) + gaps` fits the container main size; when the
  next item would overflow (and the line is non-empty), start a new line. An item
  wider than the container goes alone on its line (overflows), mirroring the
  inline `overlong_word_on_own_line` rule. Gaps count between items on a line.

```rust
struct FlexLine { items: Vec<usize> /* indices into the items vec */ }
```

### 3.5 Resolve flexible lengths per line (the grow/shrink core)

For each line, with `inner_main` = container main size and
`gaps = main_gap * (line.len() - 1)`:

```text
content_main = sum(item.outer_hyp_main)          // outer = hyp_main + main_bpm + margins
free_space   = inner_main - gaps - content_main
```

- If `free_space > 0` **and** `sum(grow) > 0`: distribute by grow. Each item's
  main content size += `free_space * (item.grow / sum_grow)`. (Items with
  `grow == 0` keep base size.) If `sum(grow) == 0`, leave free space for
  justify-content (§3.7).
- If `free_space < 0` **and** `sum(shrink) > 0`: distribute the (negative) space
  scaled by **shrink × base size** (the spec's "scaled flex shrink factor"). For
  each item `weight_i = shrink_i * base_main_i`; `sum_w = Σ weight_i`; item main
  content size += `free_space * (weight_i / sum_w)` (free_space negative → shrinks
  larger/more-shrinkable items more). Clamp each item's resulting content main
  size to `>= 0` (M3 min-content = 0; no iterative min-violation freezing — §6).
- If `free_space == 0` or no grow/shrink applies: items keep hypothetical main
  size; leftover (if any) goes to justify-content.

Set each item's **used main (content) size** = the resolved value. (Single pass;
the spec's iterative freezing of min/max-violating items is **not** done — M3 has
no per-item max and min=0, so a single proportional pass is correct except in
contrived shrink cases where total shrink underflows below 0; we clamp at 0.
Noted §6.)

### 3.6 Cross sizes + line cross size

For each item, after its main size is fixed:

1. **Lay out the item at its resolved main size** to get its cross size. Run the
   item's block layout with a containing block whose main-axis content size =
   the item's used content main size:
   - Row: `layout_block(item, cb_with_width = used_main, …)`, then re-pin its
     content width to `used_main` and read its used content **height** as the
     item's content cross size. (Like inline-block, re-pin margins to specified
     so the margin box is tight — reuse the `layout_inline_block` margin re-pin
     idea.)
   - Column: `layout_block` with the container's content **width** as the cb
     width, force the item's content **height** = `used_main`, read used content
     **width** as cross size (or the explicit width if set).
2. **Item outer cross size** = content cross + cross border/padding + cross
   margins.
3. **Line cross size** = `max(item outer cross size)` over the line. For a
   single-line row container with auto height, the container cross size (height)
   = this line cross size; for multi-line, the container cross size = sum of line
   cross sizes + `cross_gap * (lines-1)`.
4. **align stretch**: if the item's effective align (`align_self` resolved, or
   container `align_items`) is `Stretch` **and** the item's cross size property is
   auto, set the item's content cross size so its **outer** cross fills the line
   cross size, then re-lay the item at that cross size (row: re-pin height;
   column: re-pin width and re-run block layout so its inline content reflows to
   the new width). For M3, stretch in a **row** (vertical stretch) just sets the
   item's content height = line cross − cross bpm − cross margins (no reflow
   needed since height doesn't affect block content). Stretch in a **column**
   (horizontal stretch) re-runs the item's block layout at the new width.

### 3.7 Main-axis alignment (justify-content) + positioning

Per line, compute the **leftover main free space** after items took their used
main sizes:

```text
used_main_total = sum(item.outer_used_main) + gaps
leftover = inner_main - used_main_total          // >= 0 typically after grow
```

Distribute `leftover` per `justify_content` into a **leading offset** and a
**between-items spacing** added on top of `main_gap`:

```text
FlexStart    : lead = 0;                between = 0
FlexEnd      : lead = leftover;         between = 0
Center       : lead = leftover/2;       between = 0
SpaceBetween : lead = 0;                between = leftover/(n-1)   (n>1, else lead=0)
SpaceAround  : between = leftover/n; lead = between/2
SpaceEvenly  : between = leftover/(n+1); lead = between
```

Walk the line placing each item along the main axis:

```text
cursor = main_start_of_content + lead
for item in line (in order; if is_reverse, iterate reversed):
    place item's outer main-start at `cursor` (+ item.margin_main_start inside)
    cursor += item.outer_used_main + main_gap + between
```

`main_start_of_content` is the container content-box main origin
(`content.x` for row, `content.y` for column). For `*-reverse` directions the
item order along the main axis is reversed (we iterate the line's items back to
front); justify offsets are computed identically and applied from the (reversed)
start.

### 3.8 Cross-axis alignment (align-items / align-self) + final coords

For each line at cross offset `line_cross_start` (first line at the content-box
cross origin; subsequent lines stacked by previous line cross sizes + `cross_gap`):

For each item, resolve effective align = `align_self` (Auto → container
`align_items`). Compute the item's cross position within the line:

```text
free_cross = line_cross_size - item.outer_cross_size
Stretch / FlexStart / Baseline(→start, §6): cross_pos = 0
FlexEnd                                    : cross_pos = free_cross
Center                                     : cross_pos = free_cross / 2
```

Now convert (main_pos, cross_pos) → physical and `translate_box` the item's
already-laid-out subtree so its **margin-box top-left** lands at the computed
physical position:

```text
row    : phys_x = main_pos (+ margin_main_start handled), phys_y = line_cross_start + cross_pos
column : phys_x = line_cross_start + cross_pos,           phys_y = main_pos
```

Each item was laid out at a provisional origin (from step 3.6); we compute the
delta to the target margin-box top-left and call `translate_box(item, dx, dy)`
(reusing the existing `inline.rs` helper, already `pub(crate)`).

### 3.9 Container height returned

```text
row    container content height = explicit height, else the cross extent
       = sum(line cross sizes) + cross_gap*(lines-1)
column container content height = explicit height, else the main extent
       = max over lines of (sum item outer main + gaps + justify leftover==0)
```

`layout_flex` returns this so `layout_block` stores it as `content.height` (and
`calculate_block_height` lets an explicit `height` override). For a row container
the returned value is the cross (height) extent; for a column container it is the
main (height) extent. Both are "the content-box height", which is what the caller
needs.

## 4. Sizing details (how item base/cross sizes reuse block layout)

The flex algorithm leans entirely on the **existing `layout_block`** to size each
item:

- **Item base main size** (§3.3): for an auto-basis item with no explicit main
  size, run `layout_block(item, cb, …)` where `cb.content` main size = container
  main size, then read the used main extent. We **re-pin** the item's margins to
  its specified values afterward (auto→0), exactly like `layout_inline_block`
  does, so the item's margin box is tight rather than filling the container.
- **Item cross size + final size** (§3.6): re-run `layout_block` with the item's
  *resolved* main size as the containing main size (row → width; column → force
  height), so the item's internal block/inline content reflows to the right
  width. The cross size is then read from the laid-out box.
- **Stretch** (§3.6.4): one more `layout_block` pass at the stretched cross size
  for column containers (width changed → content reflows). Row stretch only sets
  the height field (no reflow).

This is the **pragmatic re-layout**: at most two block-layout passes per item
(base sizing, then final sizing; plus one for column stretch). Acceptable for M3;
no caching/min-content machinery. A flex item that is **itself a flex container**
just runs `layout_block` → flex dispatch (§3.0) recursively — **nested flex works
for free**.

Container main/cross definite sizes come from the **normal block width rule**
(`calculate_block_width` already ran on the container in `layout_block`) for the
horizontal dimension, and from explicit `height` (or content) for the vertical —
§3.2.

## 5. Paint (`starfish-paint`)

**No paint changes.** Flex items are ordinary `BlockContainer` / `InlineBlock` /
`AnonymousBlock` boxes with **absolute** content coordinates assigned by
`translate_box` (§3.8). The existing `build_display_list` / `paint_subtree`
recursive walk descends into the container's children and paints their
backgrounds/borders/text correctly, since it keys off `BoxKind` and absolute
`dimensions`, not on layout mode.

One thing to confirm: `role()` in `display.rs` reclassifies only
`BlockContainer|InlineBlock|InlineBox`. A block-level flex container is a
`BlockContainer` and an inline-flex is an `InlineBlock`, so both paint in the
in-flow pass normally; their items (block-level boxes) likewise. An item that is
*also* floated/positioned would be diverted — but flex items are never out of
flow (out-of-flow children are excluded from being items, §2/§3), so no
interaction. **No change needed.**

## 6. Edge cases & explicit non-goals

Handled:
- `display:flex` (block-level) and `display:inline-flex` (atomic inline).
- `flex-direction`: row / row-reverse / column / column-reverse.
- `flex-wrap`: nowrap / wrap (greedy line breaking).
- `justify-content`: flex-start / flex-end / center / space-between /
  space-around / space-evenly (with gaps).
- `align-items` + `align-self`: stretch / flex-start / flex-end / center
  (baseline → flex-start, see below).
- `flex-grow` / `flex-shrink` / `flex-basis`, the `flex` shorthand (incl.
  `none`/`auto`/`initial`/single-number) and `gap`/`row-gap`/`column-gap`.
- Nested flex (an item that is itself a flex container) via recursive
  `layout_block` dispatch.

Explicit **non-goals / simplifications** for M3:
- **No precise intrinsic (min/max-content) sizing.** Auto-basis content sizing
  uses the item's block-laid-out extent at the container main size, not true
  max-content. Tests use explicit `width`/`flex-basis`/`flex` basis. Item
  **min main size = 0** and there is **no `max-*` clamp** (no `min-width`/
  `max-width` properties added), so the flexible-length resolution is a single
  proportional pass (no iterative min/max-violation freezing); negative results
  are clamped to 0.
- **No `order` property** — items lay out in document order (reversed only by
  `*-reverse` directions).
- **No `align-content`** for multi-line cross distribution — lines stack from the
  cross start with `cross_gap` between them (equivalent to `align-content:
  flex-start`).
- **Baseline alignment simplified** — `align-items: baseline` / `align-self:
  baseline` are treated as `flex-start` (top/cross-start). No real baseline
  participation.
- **`flex-wrap: wrap-reverse`** deferred (parser ignores it → `Nowrap` initial).
- **No aspect-ratio**, no `min-height: auto` automatic minimum, no flex item
  margin `auto` main-axis distribution (auto margins on items resolve to 0; we do
  not implement the "auto margins eat free space before justify-content" rule —
  noted; tests avoid item auto margins).
- **Percentage `flex-basis` / percentage item sizes** resolve against the
  container's (definite) main size; an indefinite column main size makes
  percentage basis fall back to the item's content size (simplified).
- **Out-of-flow children of a flex container** (float/abs/fixed) are **not** flex
  items — they keep M2 behavior (the float/abs passes handle them; the flex
  algorithm skips them). A float inside a flex container is therefore an
  uncommon, loosely-supported combination (acceptable).
- **Container baseline / inline-flex line participation**: an `inline-flex`
  container behaves like an inline-block atom on the line (bottom/top-aligned per
  the M1 inline-block baseline simplification), not true last-baseline aligned.

## 7. Test plan (concrete)

Layout tests in `crates/layout/src/lib.rs` use the existing `FixedMeasurer`
(`per` px/char) for exact geometry; style tests in `crates/style/src/lib.rs`. All
containers/items get explicit sizes/margins:0 for exact arithmetic.

### style
- `display: flex` → `Display::Flex`; `inline-flex` → `Display::InlineFlex`.
- `flex-direction: column-reverse` → `FlexDirection::ColumnReverse`; bogus →
  initial `Row`.
- `flex-wrap: wrap` → `Wrap`; `wrap-reverse` → unchanged `Nowrap` (deferred).
- `justify-content: space-between` → `SpaceBetween`; `space-evenly` →
  `SpaceEvenly`.
- `align-items: center` → `Center`; `align-self: flex-end` → `FlexEnd`;
  `align-self` default `Auto`.
- `flex-grow: 2` → `2.0`; `flex-shrink: 0` → `0.0`; `flex-basis: 100px` →
  `Px(100)`; default basis `Auto`, grow `0`, shrink `1`.
- `flex: none` → `(0,0,auto)`; `flex: auto` → `(1,1,auto)`; `flex: 1` →
  `(1,1,0px)` (single number = grow, basis defaults to 0); `flex: 2 3 40px` →
  `(2,3,Px40)`.
- `gap: 10px` → row_gap == column_gap == `Px(10)`; `gap: 5px 8px` →
  row_gap `Px5`, column_gap `Px8`; `column-gap: 12px` → only column.
- none of the flex props inherit: a child of a `display:flex` parent computes
  `flex_grow == 0`, `align_items == Stretch` (initial), `display != Flex`.

### layout — main-axis distribution
- **Three `flex:1` items split width equally (incl. gap).** Container width 300,
  `gap:0`, three children `flex:1 1 0` → each used main width 100, positioned at
  x = 0, 100, 200. With `gap:30` → each `(300 - 60)/3 = 80`, at x = 0, 110, 220.
- **flex-grow 1 vs 2 distributes 1:2.** Container 300, two items basis 0,
  grow 1 and 2 → widths 100 and 200 (free 300 split 1:2).
- **flex-shrink shrinks overflow.** Container 100, two items `width:80` (basis
  80), shrink 1 each → total 160, overflow 60 split by `shrink*base` equally →
  each shrinks 30 → widths 50 and 50.
- **shrink:0 item keeps size.** Container 100, item A `width:80 flex-shrink:0`,
  item B `width:80 flex-shrink:1` → A stays 80, B shrinks to 20.

### layout — justify-content
- **center.** Container 300, two items `width:50` (no grow) → leftover 200,
  lead 100 → items at x = 100, 150.
- **space-between.** Container 300, three items `width:50` → leftover 150,
  between 75 → x = 0, 125, 250.
- **space-around / space-evenly.** Container 300, two items `width:50` →
  around: between=200/2=100, lead=50 → x = 50, 200; evenly: between=200/3≈66.7,
  lead=66.7 → x ≈ 66.7, 183.3.

### layout — cross alignment
- **align-items: center.** Row container height 100, item height 40 → item
  content.y = 30 (centered).
- **align-items: stretch (default).** Row container height 100, item with auto
  height → item content height = 100 (fills line cross). A second item with
  `height:40` keeps 40.
- **align-self override.** Container `align-items:flex-start`, one item
  `align-self:flex-end` → that item sits at the bottom of the line, others at top.

### layout — direction
- **column stacks vertically.** `flex-direction:column`, three items `height:30`,
  `gap:0` → content.y = 0, 30, 60; container auto height 90.
- **row-reverse.** Two items `width:50` in container 300, `justify:flex-start` →
  reversed order: first child placed at the right end. Assert the first DOM child
  has the larger x.

### layout — wrap
- **wrap to a second line.** Container width 250, three items `width:100`,
  `flex-wrap:wrap`, `gap:0` → two on line 0 (x 0, 100), third wraps to line 1
  (x 0, y = line-0 cross size). Container height = 2 × item height.

### layout — nested flex
- **flex item is itself a flex container.** Outer row container 300 with one
  `flex:1` item that is `display:flex` with two `flex:1` children → outer item
  width 300, inner children each 150. Proves recursive dispatch.
